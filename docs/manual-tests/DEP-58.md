# DEP-58: развёртывание журнала переписки — ручная проверка (стенд)

Нужны: узел с этапом журналирования в конвейере (волна `app-81`, APP-84 — до её слияния записи журнала не
пишутся: этап реализован в tp-smtp, но не подключён в собранном узле) и поверхностями правил/восстановления
(правила журналирования и `restore_index` — следующие волны; аудит влит — ADM-52 #160: `thepost admin journal
search/get/export/verify`, роль «аудитор журнала»). Стенды: профиль SMB (`--profile smb` из
`docs/manual-tests/CMP-01.md` или Ansible `smb.yml` — журнал `journal.local`) и малый Enterprise
(`small-enterprise.yml` с `small_journal_bucket` — SeaweedFS ≥ 4.x с Object Lock; образ compose 3.80 блокировки
не умеет). Инструменты: `swaks`, `psql`, `weed shell`, `thepost` на узле. Живые стенды не трогать: сценарий
прогоняется на отдельной ВМ/контейнере.

Обозначения: `D` — домен стенда, `A=a@$D`, `B=b@$D` (пароль приложения — APP-19), `PSQL` — доступ к базе узла
(`psql postgres://thepost@…/thepost`), `NODE` — команда запуска `thepost` на узле (`docker exec <узел>` или `ssh`).
Результат каждого шага — «ок» или замечание, в таблицу в конце; задержки шагов 18–19 — в отчёт стенда
(`deploy/stand/reports/<прогон>-…/`, критерии Д.7).

## Конфигурация и предупреждения (S4.9, риски 21–23)

1. **Умолчание — выключено:** без `journal.enabled` узел стартует, `thepost config check` — «конфигурация верна»,
   `NODE thepost doctor journal` — без ошибок; письма не записываются.
2. **SMB, предупреждение:** включить журнал (`thepost_journal_enabled: true` / `journal.enabled: true` с
   `journal.local`) → `NODE thepost doctor` показывает предупреждение `journal.backend`: локальный каталог
   защищает только сервер (записи лишь добавляются), от администратора ОС защиты нет — для неизменяемости
   S3 с Object Lock (риск 23). `NODE thepost doctor journal retention` — прогноз объёма на срок.
3. **Параметры S3:** бакет журнала равен бакету BLOB ящиков → `thepost config check` отвергает (блокировка общих
   BLOB сделала бы письма ящиков неудаляемыми); `lock_mode: compliance` без `retention` → отвергает (риск 21);
   одновременно `s3` и `local` → отвергает. Ansible: те же проверки — assert роли `thepost` (compliance без срока)
   и `thepost config check` на стенде.
4. **Object Lock бакета:** `small-enterprise.yml` с `small_journal_bucket: thepost-journal` — плейбук создаёт
   бакет с блокировкой (`s3.bucket.create -withLock`) и завершает шаг «Object Lock must be enabled» без ошибок;
   повторный прогон — `failed=0`, бакет не пересоздаётся. Существующий бакет без блокировки —
   `echo 's3.bucket.lock -name thepost-journal -enable' | weed shell …` включает (необратимо).
5. **Записи несут режим и срок:** после шагов 7–8 объекты записи в бакете — с метаданными
   `x-amz-meta-thepost-lock-mode` и `x-amz-meta-thepost-lock-until` (`weed s3.bucket.ls` / консоль S3); режим
   governance по умолчанию, compliance — только явно и со сроком. Попытка удалить объект записи до конца срока —
   отказ хранилища (governance — без роли обхода, compliance — всем).

## Правило Both → записи (запись)

6. **Правило:** включить правило журналирования на организацию, направление «оба» (Admin API / консоль;
   до вливания поверхности правил — вставка в `journal.rules` через `psql`, как в `deploy/stand/check10.py`);
   `PSQL -c 'SELECT id, direction FROM journal.rules'` — правило видно.
7. **Входящее:** `swaks --server <$D> --port 25 --from x@remote.test --to $B --header 'Bcc: hidden@$D'` — `250`;
   в журнале запись о письме: конверт содержит отправителя, `$B` и скрытого `hidden@$D` (поиск/просмотр — шаг 11);
   `PSQL -c 'SELECT count(*) FROM journal.entries'` растёт на 1.
8. **Исходящее:** `swaks --server <$D> --port 587 --tls --auth PLAIN --auth-user $A --auth-password … --from $A
   --to $B` — `250`; вторая запись (исходящее направление); копия в `Sent` у отправителя повторно не
   журналируется (копия журнала проходит конвейер без этапа правил).
9. **До Sieve, не отменяется:** скрипт ящика получателя с `discard` (ManageSieve) → письмо в ящик не попало,
   запись в журнале есть (этап журналирования — до Sieve ящика, S4.9).
10. **Выключение:** отключить правило → новое письмо не записывается; записи прежние на месте.

## Поиск и выгрузка (аудитор журнала)

11. **Поиск:** под учётной записью с ролью «аудитор журнала» — поиск по отправителю `x@remote.test`, по
    получателю `$B`, по `Message-ID` письма из шага 7, по интервалу «последний час» — каждая выборка находит
    соответствующие записи; каждое обращение попадает в журнал аудита. Администратору организации и
    пользовательскому токену — отказ (403), в IMAP/JMAP журнала нет.
12. **Выгрузка:** `NODE thepost admin journal export <id записи шага 7> > journal.eml` — файл начинается с
    заголовков конверта `X-ThePost-Journal-Sender/-Recipient/-Message-Id/-Rule/-Date` (получатели — все,
    включая скрытого), далее исходное письмо байт в байт (сравнить с отправленным).

## Восстановление индекса (restore_index)

13. **Порча индекса как авария:** `PSQL -c 'DELETE FROM journal.entries'` → поиск по журналу пуст,
    `NODE thepost doctor journal` — расхождение индекса с хранилищем записей (`journal.index`).
14. **Восстановление:** `restore_index` (обслуживание; поверхность следующих волн — до влития временно
    напрямую по контракту `JournalStore::restore_index`, как в тестах tp-blob/tp-meta) → все записи из
    хранилища в индексе, поиск шага 11 снова находит их, `NODE thepost doctor journal chain` — цепочка целостна.

## Целостность цепочки (verify chain)

15. **Порча записи:** `PSQL -c "UPDATE journal.entries SET sender='spoof@remote.test' WHERE …"` →
    `NODE thepost doctor journal chain` — разрыв обнаружен (номер записи, подмена столбца);
    `NODE thepost admin journal verify` — отчёт целостности с тем же разрывом.
16. **Удаление записи индекса:** `PSQL -c 'DELETE FROM journal.entries WHERE …'` (одна строка) → цепочка
    последующих записей тоже «рвётся» (звено исчезло) — обнаруживается; `restore_index` пересобирает индекс
    из хранилища — `chain` снова целостен. Порча самого объекта хранилища невозможна при включённом Object Lock
    (шаг 5) — это и есть защита.

## Задержка конвейера с журналированием и без (риск 22)

17. **Прогон без журнала:** `stand.yml` базовый сценарий Д.6 (профиль `speed`), журнал выключен — p95 «приём
    SMTP до ответа 250» и «внутренняя доставка до появления в ящике» в отчёт.
18. **Прогон с журналом:** то же с правилом Both на организацию и включённым журналом (S3 с Object Lock) —
    те же метрики в отчёт; разница против шага 17 — в отчёт стенда. Критерии Д.7 должны выполняться в обоих
    прогонах (p95 приёма < 500 мс, доставки < 5 с); заметный рост разницы — находка в отчёт (правила на всё
    письмо считаются один раз — рассылки не умножают работу, S4.10).
