# 4. Функциональные требования

## 4.1. Почтовый транспорт (SMTP)

Приём — SMTP (25) с STARTTLS; отправка клиентами — submission (587, STARTTLS) и submissions (465, неявный TLS) с обязательной аутентификацией SASL.

Аутентификация входящей почты выполняется ядром: SPF (RFC 7208), DKIM (RFC 6376), DMARC (RFC 7489), ARC (RFC 8617). Исходящая почта подписывается DKIM. Безопасность доставки — MTA-STS (RFC 8461), DANE (RFC 7672), TLS-RPT (RFC 8460).

Антиспам и антивирус подключаются по протоколу Milter: цепочка фильтров с таймаутами и политикой при недоступности фильтра (принять с пометкой или временный отказ). Собственных средств фильтрации продукт не содержит.

В DMZ приём выполняют узлы edge (п. 2.6).

Очередь исходящей почты хранится в PostgreSQL, тела — в BLOB. Обработка распределяется между узлами smtp-out через лизы записей; повторы по расписанию, уведомления о недоставке (DSN, RFC 3464). Исходящие соединения устанавливаются с фиксированных адресов (egress-IP), согласованных с PTR и SPF.

Экран соединений (по модели postscreen Postfix): до приветствия сервера и в начале сессии отклоняются клиенты, начавшие передачу до приветствия, нарушившие порядок команд (pipelining без поддержки) или превысившие частоту соединений; результат кэшируется по IP-адресу на заданный срок. Репутационные списки DNS (DNSBL, DNSWL) — средствами Rspamd через Milter.

Проверки при приёме выполняются до ответа 250 — отказ вместо уведомления о недоставке: существование получателя, превышение квоты ящика получателя (временный или постоянный отказ по настройке), ограничения группы рассылки на отправителей (п. 4.5).

Адресация: псевдонимы, адрес для всей почты домена (catch-all), подадреса (user+tag, разделитель настраивается), переписывание адресов; источник — каталог (п. 5.1) и Admin API.

Планировщик исходящей очереди (по модели qmgr Postfix): лимиты параллельности и скорости на домен назначения, медленный старт новых доменов, отложенная обработка недоступных доменов, раздельные очереди внутренней и внешней доставки; недоступный домен не задерживает доставку в другие.

Политики по доменам назначения (по модели коннекторов Exchange): обязательный TLS или закреплённый сертификат для партнёров, маршрут через промежуточный узел (smart host), собственный egress-IP. Политика для всех внешних доменов задаёт общий промежуточный узел (relayhost Postfix).

Принятые домены (по модели Exchange): полномочный — получатели только из каталога, неизвестный адрес отклоняется в RCPT TO; внутренняя ретрансляция — неизвестные адреса домена передаются на указанный узел (совместная работа со старым почтовым сервером на время миграции).

Доверенные источники (по модели соединителей приёма Exchange) задаются адресами или сертификатом клиента (mTLS):

- шлюз — внешний MTA перед продуктом (п. 2.6): исходные адрес и имя клиента принимаются из команд XCLIENT или XFORWARD; SPF, DMARC, экран соединений и лимиты применяются к исходному клиенту, а не к шлюзу; при отсутствии этих данных принимаются результаты проверок шлюза (Authentication-Results с заданным authserv-id, ARC); от источников вне списка команды XCLIENT и XFORWARD отклоняются;
- приложение — устройства и системы без SASL (МФУ, учётные системы): отправка без аутентификации с перечисленных адресов, только от разрешённых адресов отправителя; внешние получатели — по явному разрешению источника.

Правила потока почты (по модели mail flow rules Exchange) — модуль (п. 1.3, 4.10); точки вызова — этапы конвейера обработки (п. 4.9). Без модуля правила не применяются, журналирование (п. 4.9) выполняется всегда.

Пересылка (перенаправление Sieve, правило потока): адрес отправителя в конверте переписывается по схеме SRS, письмо подписывается ARC — получатель проходит проверки SPF и DMARC.

Настройки транспорта (принятые домены, политики доменов назначения, доверенные источники) — данные организации в PostgreSQL: меняются через Admin API и вступают в силу на всех узлах по сигналу (п. 2.8) без перезапуска. В config.yaml — только параметры узла (адреса, порты, лимиты, таймауты).

Обучение антиспама (по модели imapsieve Dovecot): перемещение письма пользователем в папку «Спам» и из неё передаётся в Rspamd на обучение через события ядра (п. 2.5); включается настройкой.

Фильтры Milter подключаются отдельными профилями для приёма и для исходящей почты (submission и JMAP EmailSubmission); профиль исходящей почты служит, в частности, для подключения внешних систем DLP. Другие способы подключения DLP — маршрут через промежуточный узел (политика домена назначения) и копия через журналирование (п. 4.9).

Отложенная отправка: письмо ставится в очередь со сроком выпуска (JMAP `EmailSubmission.sendAt`, предел — `maxDelayedSend`) и до срока может быть отменено пользователем (`undoStatus` = `canceled`), в том числе как «отмена отправки» в течение нескольких секунд.

Личные списки надёжных и заблокированных отправителей ящика (адреса и домены) применяются при доставке поверх вердикта антиспама: письмо заблокированного отправителя помещается в папку «Спам», надёжного — во «Входящие». Управление — JMAP-расширение и Admin API; возврат письма пользователем из «Спама» может предлагать добавление отправителя в надёжные.

**Обоснование.** Проверки SPF, DKIM, DMARC требуют разбора SMTP-сессии и содержимого письма и не могут выполняться прокси-слоем. Персистентная очередь в общей БД позволяет узлам smtp-out оставаться без состояния: при отказе узла письма обрабатывают другие узлы. Milter поддерживается Rspamd, clamav-milter и большинством промышленных фильтров, поэтому заказчик использует имеющиеся средства.

Функции транспорта выбираются по правилу: функция входит в ядро, если она нужна сценарию замены Exchange или обязательна по RFC и требованиям безопасности и не может быть вынесена в точку расширения без потери корректности (требует состояния SMTP-сессии или очереди); иначе — Milter, правила потока, Sieve, модуль или внешний MTA на периметре (п. 2.6). Около тысячи параметров Postfix в основном описывают реализацию (процессы, таблицы поиска, совместимость с sendmail) и не переносятся; соответствие типовых параметров — приложение Ж. Правила потока — модуль, а не фильтр Milter: условиям нужны каталог (группы, внутренний или внешний адресат), действиям — маршрут и очередь модерации. Настройки транспорта хранятся данными организации, а не файлом узла: в кластере они одинаковы на всех узлах и меняются без перезапуска.

## 4.2. Доступ к почте

Протоколы доступа:

- IMAP4rev2 (RFC 9051) с расширениями IDLE, CONDSTORE/QRESYNC, MOVE, SPECIAL-USE, NAMESPACE, ACL, QUOTA, LITERAL+, COMPRESS;
- JMAP Core (RFC 8620), JMAP Mail (RFC 8621), push по WebSocket (RFC 8887) и EventSource — основной протокол для приложений и веб-клиента;
- POP3 (RFC 1939) — для устаревших устройств, выключен по умолчанию.

Долгоживущие соединения (IMAP IDLE, JMAP push) корректно завершаются при остановке узла: прекращение приёма новых соединений, уведомление клиентов (IMAP BYE), ожидание в пределах настраиваемого срока.

Статус доставки отправленного письма доступен пользователю: JMAP `EmailSubmission.deliveryStatus` по каждому получателю (принято, отложено, доставлено, отказ — с ответом удалённого сервера) формируется из журнала доставки (п. 5.2).

Автонастройка клиентов — пользователь вводит адрес и пароль, клиент находит серверы сам:

- записи DNS SRV для IMAP, submission (RFC 6186), CalDAV и CardDAV (RFC 6764);
- автонастройка по модели Thunderbird (`autoconfig.<домен>/mail/config-v1.1.xml`);
- `/.well-known/jmap`, `/.well-known/caldav`, `/.well-known/carddav`;
- профиль `.mobileconfig` для iOS и macOS (почта, календари, контакты), подписанный сертификатом организации;
- команда thepost doctor проверяет записи DNS автонастройки. Протокол Autodiscover Microsoft не поддерживается (п. 4.8).

**Обоснование.** JMAP заменяет MAPI over HTTP и EWS: пакетные JSON-запросы, синхронизация по состояниям, минимальный трафик. IMAP4rev2 обеспечивает совместимость с любыми клиентами. Push и IDLE требуют постоянных соединений, поэтому межузловая доставка уведомлений вынесена в шину событий.

## 4.3. Серверные правила (Sieve)

Правила ящика (скрипт пользователя) выполняются при доставке входящей почты на языке Sieve (RFC 5228) с расширениями fileinto, envelope, imap4flags, vacation (RFC 5230), redirect, body, relational. Управление — ManageSieve (RFC 5804) и JMAP Sieve (RFC 9661). Интерпретатор — собственная реализация.

Обязательные правила администратора — модуль «Правила потока почты» (п. 4.10): выполняются тем же интерпретатором в отдельном доверенном контексте до и после скрипта ящика; через ManageSieve и JMAP Sieve пользователю не видны и не изменяются; расширение vnd.thepost.admin в скриптах ящика запрещено — ManageSieve его не объявляет, компиляция скрипта с ним отклоняется.

**Обоснование.** Правила сортировки, пересылки и автоответа должны работать при выключенном клиенте и одинаково на всех устройствах — аналог правил папки «Входящие» Exchange. Sieve — открытый стандарт с поддержкой в клиентах. Готовая реализация sieve-rs распространяется под AGPL-3.0 и не соответствует лицензионной политике (п. 7.1).

## 4.4. Календари, контакты, задачи

Календари — CalDAV (RFC 4791), планирование встреч CalDAV Scheduling (RFC 6638), iTIP/iMIP (RFC 5546, RFC 6047) для внешних участников, free/busy, бронирование ресурсов (переговорных) с автоматическим принятием по правилам ресурса. JMAP Calendars — по мере стабилизации спецификации IETF.

Контакты — CardDAV (RFC 6352), JMAP Contacts (RFC 9610). Глобальная адресная книга (GAL) формируется из каталога LDAP и публикуется как адресная книга CardDAV только для чтения.

Задачи и заметки — только транспорт синхронизации (CalDAV VTODO, JMAP Tasks); бизнес-логика, группировка, тегирование и отображение — на стороне клиента.

Глобальная адресная книга содержит учётные записи, группы и почтовые контакты (п. 4.5) и организационные атрибуты каталога: подразделение, должность, руководитель. Путь подразделения публикуется в vCard (`ORG`: организация; департамент; отдел), дерево подразделений с порядком старшинства (атрибут каталога задаётся настройкой) — JMAP-расширением и Admin API (иерархическая адресная книга).

Внешний доступ к календарям:

- публикация календаря по ссылке ICS только для чтения: токен в ссылке, отзыв, уровень детализации «занят / свободен», «тема и время», «полностью»;
- ссылка занятости (VFREEBUSY) пользователя публикуется в vCard (`FBURL`) и в каталоге (`calFBURL`); её используют внешние клиенты и серверы, в том числе функция Internet Free/Busy Outlook;
- политика организации (организация → ящик): разрешение публикации, максимальный уровень детализации, срок жизни ссылки, домены, которым доступна занятость; выдача и отзыв ссылок записываются в журнал аудита.

Клиенты получают внешнюю занятость и управляют публикацией через JMAP-расширения (наличие — в `capabilities` сессии):

- `urn:thepost:availability`, метод `Availability/get`: адреса и интервал → периоды занятости с указанием источника и уровня детализации; источник выбирает сервер — пользователи организации, ссылки занятости (FBURL из GAL и контактов, шаблон домена-партнёра из политики), модуль «Федерация календарей»; адрес без доступной занятости — «нет данных», а не «свободен»;
- `urn:thepost:calendarpublish`: создание, список и отзыв ссылок публикации календаря с уровнем детализации в пределах политики;
- внешние ссылки занятости сервер запрашивает только по HTTPS, с таймаутом и кэшем; внутренние и частные адреса запрещены (защита от SSRF).

Занятость между организациями без ручной настройки ссылок — модуль «Федерация календарей» (п. 1.3): собственный протокол на основе VFREEBUSY и подписей HTTP Message Signatures (RFC 9421) с ключом в DNS, коннекторы к Exchange Server (EWS) и Microsoft 365 (Graph).

**Обоснование.** CalDAV и CardDAV — промышленные стандарты с нативной поддержкой в macOS, iOS, Thunderbird, Evolution. Ограничение задач транспортом защищает ядро от логики таск-менеджера, которая вне назначения продукта.

## 4.5. Общие ящики и делегирование

Поддерживаются общие ящики, делегирование прав (Send As, Send on Behalf), ACL папок (RFC 4314) и общих календарей. Права проверяются единым слоем авторизации для всех протоколов.

Группы рассылки формируются из групп каталога (п. 5.1): ограничение круга отправителей (внутренние, список, группа), модерация (письмо доставляется после одобрения модератором), скрытие из GAL; вложенные группы раскрываются с защитой от циклов.

Почтовые контакты — внешние адресаты в адресной книге организации: синхронизируются из каталога (класс объектов и ветка задаются настройкой) или создаются через Admin API; входят в GAL и в состав групп.

Динамические группы рассылки: состав определяется фильтром по атрибутам каталога (подразделение, должность, офис, произвольный атрибут) и вычисляется при раскрытии; создаются через Admin API; ограничения отправителей и модерация — как у групп каталога. Самообслуживание групп (создание и вступление пользователями) не поддерживается: группы ведутся в каталоге.

## 4.6. Полнотекстовый поиск

Поиск выполняется на сервере встроенной библиотекой Tantivy во всех профилях. Единица индекса — ящик; общий ящик имеет собственный индекс.

- индексируется неизменяемое содержимое: тема, адреса, тело, текст вложений; дата — поле сортировки; флаги и папки не индексируются — фильтры по ним выполняются в PostgreSQL, результаты пересекаются;
- текст вложений (PDF, DOCX, XLSX, PPTX, ODF, HTML, TXT) извлекается ролью indexer в изолированном подпроцессе (seccomp, лимиты памяти и времени);
- задания индексации передаются через таблицу outbox в PostgreSQL; индекс ящика в каждый момент изменяет один индексатор (лиза);
- коммит индекса выполняется пакетами (по времени или числу документов); неизменяемые сегменты сохраняются в BlobStore под префиксом ящика, манифест версии — в PostgreSQL;
- узлы search держат горячие индексы в LRU-кэше на NVMe; ящик закрепляется за узлом консистентным хэшированием; при отказе узла индекс загружается другим узлом из BlobStore;
- большие общие ящики закрепляются за узлом с тёплой репликой на втором узле;
- морфология — стеммеры Snowball (русский, английский и другие языки);
- поиск по множеству ящиков (eDiscovery) выполняется фоновым заданием модуля «Соответствие требованиям» (п. 1.3).

Индекс — производные данные и перестраивается из PostgreSQL и BLOB.

**Обоснование.** Почтовый поиск всегда ограничен ящиком пользователя, поэтому распределённый поисковый кластер с рассылкой запросов по шардам избыточен. Индекс ящика невелик (сотни мегабайт на 100 тыс. писем), независим и переносим. Хранение сегментов в BlobStore даёт один код для всех профилей, отказоустойчивость без собственной репликации индексов и миграцию поиска без переиндексации; отдельный JVM-кластер и его эксплуатация не нужны. Принцип индекса на ящик с хранением в объектном хранилище применяется в промышленных почтовых системах (Dovecot).

## 4.7. Корзина, архив, политики хранения, Legal Hold

- удалённые пользователем элементы (письма, папки, события, контакты) хранятся в корзине в течение срока, заданного политикой (по умолчанию 30 суток); восстановление — пользователем через клиент (JMAP) или администратором через Admin API;
- по истечении срока элементы удаляются окончательно (п. 3.4); перед окончательным удалением выполняется точка принятия решений (п. 2.5);
- политики хранения (на уровне организации, группы, ящика, папки) и Legal Hold (приостановка окончательного удаления для ящика или выборки по критериям с фиксацией в журнале аудита) реализуются модулем «Соответствие требованиям» (п. 1.3).
- при заполнении ящика на 80 и 95 % (пороги настраиваются) пользователю направляется предупреждение; при превышении квоты приём отклоняется до ответа 250 (п. 4.1).
- архив ящика — ветка папок с атрибутом `\Archive` (RFC 6154) и собственной квотой; письма переносятся в архив по возрасту по политике (организация → ящик); клиент может не синхронизировать архив, поиск охватывает его; холодный уровень хранения архива — модуль «Соответствие требованиям»;
- ящик учётной записи, исчезнувшей из каталога, отключается (вход запрещён, приём — отказ 550) и хранится в течение срока политики (по умолчанию 30 суток): его можно восстановить, подключить к другой учётной записи или выгрузить; по истечении срока ящик удаляется окончательно через точку принятия решений (п. 2.5).

**Обоснование.** Бессрочное мягкое удаление противоречит требованиям 152-ФЗ о прекращении обработки персональных данных и политикам хранения. Корзина закрывает наиболее частый сценарий восстановления без обращения к резервным копиям.

## 4.9. Конвейер обработки и журналирование

Каждое письмо проходит конвейер обработки — упорядоченные этапы, общие для приёма извне (smtp-in), отправки клиентом (submission, JMAP EmailSubmission) и доставки в ящик. Этапы ядра: проверки сессии (MAIL, RCPT), Milter, журналирование, Sieve ящика, итоговый контроль действий, доставка или постановка в очередь. Модули регистрируют собственные этапы (п. 2.5):

- стадии SMTP: на MAIL и RCPT — условия по конверту, отказ отдельному получателю; на DATA — условия по содержимому, отказ относится ко всему письму; входящая почта обрабатывается до доставки в ящик, исходящая — до постановки в очередь;
- конвейер выполняется ролью transport; узел edge передаёт сессию насквозь (п. 2.6), поэтому отказ возвращается отправителю синхронно в той же SMTP-сессии;
- итоговый контроль действий — после всех этапов проверяется итоговый набор действий (перенаправления, копии, адресаты) по политикам организации, в том числе запрет внешней пересылки (п. 4.10);
- служебные письма продукта (DSN, отбивки, уведомления) и копии журнала проходят конвейер без этапов правил — петли исключены.

Журналирование (по модели journaling Exchange) — базовая поставка:

- правило журналирования задаётся на организацию, группу или ящик с направлением (входящие, исходящие, оба); выполняется этапом ядра до Sieve ящика и этапов модулей, поэтому скрипт ящика (discard, stop) и правила модулей его не отменяют;
- одна запись на письмо: письмо целиком и конверт (отправитель, все получатели, включая скрытых и раскрытых из групп), Message-ID, время, правило; записи хранятся в отдельном бакете S3 журнала с блокировкой объектов (S3 Object Lock);
- режим блокировки задаёт заказчик: compliance — объект не удаляет никто, включая администратора хранилища, до окончания срока; governance — удаление только ролью с правом обхода блокировки, с записью в журнал аудита; срок хранения задаётся при записи и может только продлеваться;
- дедупликация внутри бакета журнала: части письма (тело, вложения) хранятся объектами по хешу содержимого, новая ссылка продлевает срок блокировки объекта до наибольшего из ссылающихся записей; объекты с BLOB ящиков не разделяются — удаление письма пользователем не затрагивает журнал, блокировка не затрагивает хранилище ящиков;
- индекс журнала — в PostgreSQL (схема journal) для поиска, eDiscovery и проверки правил на выборке; записи индекса связаны цепочкой хешей, целостность проверяют thepost doctor и Admin API; индекс восстанавливается из бакета;
- доступ к журналу — только роль «аудитор журнала» (п. 5.2): поиск, просмотр, выгрузка; каждое обращение записывается в журнал аудита; пользователям и администратору правил журнал недоступен, через IMAP и JMAP не виден;
- выгрузка во внешний архив заказчика (.eml с конвертом) — по настройке;
- профиль SMB с локальным диском: блокировку выполняет сервер (только добавление), что не защищает от администратора ОС; thepost doctor предупреждает; для требований неизменяемости — S3 с Object Lock (SeaweedFS).

**Обоснование.** Журналирование — обязательное требование ИБ и регуляторов к корпоративной почте и входит в базовую поставку Exchange, поэтому не выносится в модуль. Запрет удаления на уровне сервера не защищает от администратора СУБД и хранилища; блокировка объектов S3 в режиме compliance защищает и от него. SeaweedFS поддерживает Object Lock (governance, compliance, legal hold). Отдельный бакет нужен потому, что блокировка общих BLOB сделала бы неудаляемыми письма ящиков и связала бы уборщик мусора ящиков со сроками журнала; дедупликация внутри журнала сохраняет экономию на повторяющихся вложениях и рассылках.

## 4.10. Правила потока почты (модуль)

Модуль «Правила потока почты» (п. 1.3) — обязательные правила администратора для организации, групп и ящиков: пользователь не может их отключить, изменить или обойти скриптом ящика. Клиенты не изменяются: правила пользователя — Sieve ящика (п. 4.3), правила администратора пользователю не видны (решение 2026-11-11).

Модель:

- области: организация → группа или подразделение (с вложенностью) → ящик; источник — группы и подразделения каталога, включая динамические группы и иерархию адресной книги (п. 4.4, 5.1); при мультитенантности над организацией — уровень инсталляции (п. 3.8); правило наследуется всеми членами области;
- только дополнение: нижний уровень не переопределяет и не отключает правило верхнего; исключение (exclude — ящики или группы) задаётся в самом правиле, то есть на его уровне или выше;
- правило: номер (R-0042), имя, область, фаза (before, after), направление (in, out, both), условия, действия, приоритет, состояние, режим отбивки, текст для пользователя (user_message), автор, версия;
- язык — Sieve (RFC 5228) с расширением vnd.thepost.admin (серверные действия); хранятся исходный текст и скомпилированный вид; в веб-консоли — конструктор «условия — исключения — действия» (по модели mail flow rules Exchange), формирующий Sieve, и редактор исходного текста.

Порядок исполнения входящей почты (для каждого ящика-получателя): before организации → before групп (сверху вниз) → before ящика → Sieve ящика → after ящика → after групп (снизу вверх) → after организации.

- before-правила выполняются в доверенном контексте, отдельном от скрипта ящика: stop пользователя на них не влияет; stop в правиле администратора прекращает только цепочку текущего уровня; скрипт ящика пропускается только действием skip_user_rules;
- after-правила выполняются всегда, в том числе после discard в скрипте ящика, и видят итоговый набор действий; отменить discard пользователя они не могут;
- правила с действием на всё письмо (отказ на стадии DATA, карантин) вычисляются один раз на письмо; если по содержимому отклоняется часть получателей, входящая копия им не доставляется без DSN внешнему отправителю, для исходящей отправителю направляется отбивка;
- исходящая почта: правила применяются на стадиях MAIL, RCPT, DATA при submission и JMAP EmailSubmission до постановки в очередь; Sieve ящика не участвует, фазы before и after выполняются подряд.

Действия (в дополнение к действиям Sieve — fileinto, redirect, addflag и др. — и transport rules Exchange — дисклеймер, дополнение темы, модерация (п. 4.5), маршрут по политике домена назначения):

- journal — дополнительная запись в журнал (п. 4.9) по условиям правила;
- quarantine — карантин с причиной и номером правила; хранение — как у журнала; выпуск — только аудитором журнала, письмо продолжает конвейер после сработавшего правила;
- reject, discard — для исходящей: отказ отправителю (SMTP-ответ с номером правила при синхронной отправке, иначе отбивка); для входящей: отказ в SMTP-сессии, DSN внешнему отправителю не направляется;
- add_header — метки DLP, классификации и аудита; анализ содержимого — внешними DLP (п. 4.1);
- block_external_forward — запрет перенаправления и пересылки на внешние адреса, проверяется в итоговом контроле действий (п. 4.9) и перехватывает перенаправление из скрипта ящика;
- notify_admin — уведомление администратору или в SIEM (syslog, CEF);
- skip_user_rules — пропуск скрипта ящика.

Отбивка пользователю:

- режимы: silent — ничего; rule_id — «Письмо не отправлено (задержано) по правилу R-0042. Обратитесь к администратору»; full_text — то же, имя правила и user_message (не исходный текст правила); режим задаётся в правиле, по умолчанию наследуется от области; для journal и add_header по умолчанию — silent;
- отбивка — письмо в формате DSN (RFC 3464) от служебного адреса; при синхронном отказе исходящего — дополнительно SMTP-ответ с номером правила; шаблоны с локализацией редактируются в веб-консоли;
- уведомление получателя о карантине входящего — по умолчанию выключено, включается в правиле; режимы rule_id и full_text, тема и отправитель по умолчанию не показываются, ссылок на содержимое нет; ежедневная сводка вместо уведомления на каждое срабатывание.

Администрирование (веб-консоль и Admin API, п. 5.2; пользовательскому токену недоступно):

- дерево областей с правилами и источником наследования каждого правила; эффективные правила ящика — итоговая цепочка с источником каждого правила;
- проверка на выборке (dry-run) — прогон правила по последним N письмам области без изменения почты, результат — число совпадений и список; конверт и данные SMTP-сессии берутся из журнала доставки (п. 5.2); выборка — письма, сохранившиеся в ящиках или журнале; условия, для которых нет данных сессии, отмечаются как непроверенные;
- журнал срабатываний: время, правило, Message-ID, тема, действие; фильтры и экспорт; для journal по умолчанию — только счётчики; хранится на шарде ящика (п. 3.6), при большом потоке передаётся через модуль «Коннектор событий»;
- аудит изменений: автор, время, diff, версия; откат к версии; изменение правил организации — по настройке с утверждением вторым администратором (принцип четырёх глаз);
- правила, области и исключения хранятся на шарде 0 вместе с каталогом (схема mod_flowrules); скомпилированные цепочки кэшируются на узлах; изменение правила или состава группы рассылает сигнал (п. 2.8), кэш эффективных правил сбрасывается без перезапуска.

**Обоснование.** Sieve — один язык и один интерпретатор для правил ящика и администратора; конструктор консоли сохраняет привычную администраторам Exchange модель «условия — действия» без второго языка правил. Доверенный контекст и запрет расширения vnd.thepost.admin в скриптах ящика исключают обход правил пользователем. Запрет внешней пересылки проверяется по итоговому набору действий, так как перенаправление скрипта ящика возникает после before-правил. DSN внешнему отправителю при отказе входящей почты рассылал бы отбивки на подделанные адреса (backscatter). Разделение ролей администратора правил и аудитора журнала следует принципу минимальных привилегий: настройка правил не даёт доступа к содержимому писем.
