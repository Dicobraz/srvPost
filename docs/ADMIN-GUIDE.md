## О документе

ThePost управляется тремя способами: командной строкой `thepost`, веб-консолью администратора и текстовой консолью `thepost admin tui`. Все три работают через один и тот же Admin API узла, поэтому права, проверки и записи в журнал аудита у них одинаковые. Выбирайте интерфейс по задаче, а не по возможностям.

| Интерфейс | Когда удобен | Где работает |
| --- | --- | --- |
| `thepost` (узел) | установка, запуск, проверка конфигурации и хранилища | на сервере, от пользователя `thepost` |
| `thepost admin` | учётные записи, политики, очередь — из скриптов и вручную | на сервере или на рабочем месте с доступом к Admin API |
| Веб-консоль | повседневное администрирование мышью | браузер |
| `thepost admin tui` | то же, что консоль, но в терминале по SSH | терминал |

Документ описывает версию 0.2.0. Справочник собран по коду ветки `main` на 14.11.2026.

## Начало работы

Первого администратора заводит `thepost admin init` на самом сервере, дальше все интерфейсы входят по паролю или через OIDC и работают с сессией `tps_…`.

### Первый администратор

1. На сервере от root или от учётной записи службы: `sudo thepost admin init --email admin@example.ru --name "Администратор"`. Узел должен быть запущен с ролью `admin`: команда идёт через локальный сокет (`admin.init.socket`). Без `--email` адрес — `admin@<domain из config.yaml>`.
2. Команда заводит учётную запись с ролью администратора установки и принятый домен её адреса и один раз показывает пароль и токен `tpa_…` (живёт `admin.init.token_ttl`, по умолчанию 10 мин). Сохраните пароль сразу.
3. Повторный запуск даёт отказ `409`; перевыпуск — `--force`: прежние пароли `admin init` отзываются. Каждый вызов пишется в журнал аудита.

Токен `tpa_…` CLI не принимает: он нужен только для первого входа в веб-консоль, когда вход по паролю выключен. В CLI входите по паролю из шага 2.

### Вход и сессия

```sh
thepost admin login --user admin@example.ru      # пароль спросит без эха; выдаст tps_…
export THEPOST_ADMIN_TOKEN=tps_…
thepost admin whoami
```

| Токен | Откуда | Срок | Где принимается |
| --- | --- | --- | --- |
| `tpa_…` | `thepost admin init` | 10 мин, один раз | только первый вход в веб-консоль |
| `tps_…` | `thepost admin login --user` или вход в консоль | 8 ч (`admin.init.session_ttl`) | CLI, TUI, веб-консоль |
| токен OIDC | `thepost admin login --oidc` (вход с устройства, RFC 8628) | по поставщику | CLI, TUI |

- В сценариях пароль передаётся первой строкой stdin: `--password-stdin`. Аргументом пароль не передаётся.
- `--oidc` требует `auth.oidc` и `cli.oidc.client_id` в `config.yaml`; адрес и код печатаются в stderr, токен — в stdout: `export THEPOST_ADMIN_TOKEN="$(thepost admin login --oidc)"`.
- Отказы входа: `401` — неверный пароль или временная блокировка после неудачных попыток; `403` — у учётной записи нет ролей `admin.roles`; `404` — вход по паролю выключен (`admin.password_login`).
- Выхода (`logout`) и списка сессий в CLI нет: сессия истекает сама через 8 ч. Сессии хранятся в памяти узла: после его перезапуска войдите снова.

### Общие ключи `thepost admin`

Ставятся в любом месте строки; у большинства есть переменная окружения.

| Ключ | Переменная | По умолчанию | Что делает |
| --- | --- | --- | --- |
| `--url <адрес>` | `THEPOST_ADMIN_URL` | `http.admin.listen` из `config.yaml` | адрес Admin API (`https://`, при `allow_plaintext` — `http://`) |
| `--token <токен>` | `THEPOST_ADMIN_TOKEN` | — | сессия `tps_…` или токен OIDC; ключ виден в списке процессов — лучше переменная |
| `--org <UUID>` | `THEPOST_ADMIN_ORG` | организация администратора | организация запросов |
| `--json` | — | выкл. | ответ Admin API в JSON вместо таблицы |
| `--ca-file <PEM>` | — | — | корневые сертификаты для TLS Admin API |
| `--insecure` | — | выкл. | не проверять сертификат (как `curl -k`), только для loopback |
| `--timeout <сек>` | — | 30 | предельное время запроса |
| `-c, --config <путь>` | `THEPOST_CONFIG` | `/etc/thepost/config.yaml` | откуда брать адрес и настройки OIDC |
| `--color auto\|always\|never` | `NO_COLOR`, `CLICOLOR_FORCE` | `auto` | цвет вывода: в файл и конвейер при `auto` — без цвета; `NO_COLOR` сильнее `CLICOLOR_FORCE`, `TERM=dumb` — без цвета |

Учётная запись в аргументах — UUID или имя входа (без учёта регистра), группа — UUID, имя или адрес, домен — UUID или имя.

## Справочник: команды узла `thepost`

Команды узла выполняются на сервере и читают `config.yaml`: путь — `-c, --config`, затем `THEPOST_CONFIG`, затем `/etc/thepost/config.yaml`. Отдельной команды `migrate` нет: миграции базы применяются при запуске узла (`meta.migrate_on_start`).

| Команда | Назначение | Ключи | Код выхода | Пример |
| --- | --- | --- | --- | --- |
| `thepost serve` | запуск узла с ролями из `config.yaml`, работает до SIGTERM | — | 0 — штатная остановка; 1 — не запустился или роль упала | `thepost serve -c /etc/thepost/config.yaml` |
| `thepost config check` | строгая проверка: неизвестный или неверный параметр — ошибка; при успехе список ссылок на секреты | `--color` | 0 — верна; 1 — ошибки | `thepost config check -c deploy/config/all.yaml` |
| `thepost config schema` | JSON Schema `config.yaml` для редакторов | — | 0 / 1 | `thepost config schema > schema.json` |
| `thepost doctor` | проверка окружения: конфигурация, секреты, СУБД, BLOB, часы, песочница процесса, DNS домена (MX, SPF, DKIM, DMARC, MTA-STS, PTR; при роли `dav` — SRV), сертификаты, PROXY v2, PKI, приёмники аудита | `--json`, `--color` | 0 — нет проверок `fail`; 1 — есть | `sudo -u thepost thepost doctor` |
| `thepost verify` | сверка хранилища писем с учётом объектов в обе стороны | `--fix` — удалить «сирот» и пометить повреждённые; `--json` | 0 — расхождений нет или с `--fix` все исправлены; 1 — есть расхождения или ошибки | `thepost verify --json` |
| `thepost admin init` | первый администратор и принятый домен через локальный сокет | `--email`, `--name`, `--force`, `--socket` | 0 / 1 | `sudo thepost admin init --email admin@example.ru` |
| `thepost admin openapi` | схема Admin API (OpenAPI, JSON), узел и токен не нужны | `-o, --output <файл>` | 0 / 1 | `thepost admin openapi -o openapi.json` |
| `thepost admin tui` | текстовая консоль администратора ([раздел ниже](#текстовая-консоль-thepost-admin-tui)); на узле с `config.yaml` — и правка его конфигурации | ключи подключения `thepost admin`, `--theme` | 0 / 1 | `thepost admin --insecure tui` |

`--color auto|always|never` у `config check` и `doctor` работает так же, как у `thepost admin`. `thepost --version` печатает версию, `--help` у любой команды — справку по-русски.

Служебная скрытая команда `thepost search-extract` — подпроцесс индексатора для вложений, вручную не вызывается.

## Справочник: команды `thepost admin`

Синтаксис: `thepost admin [общие ключи] <ресурс> <действие> <аргументы> [ключи]`. 43 команды в 12 группах; все изменения пишутся в журнал аудита. Команды `set` выводят только изменённые поля (`-` было, `+` стало) и итог «✓ Сохранено · запись аудита …».

### Вход — `login`, `whoami`

| Команда | Что делает | Ключи |
| --- | --- | --- |
| `login --user <адрес>` | вход по паролю, выдаёт `tps_…` | `--password-stdin` |
| `login --oidc` | вход у поставщика OIDC с устройства | — |
| `whoami` | текущий администратор, организация, роли | — |

### Учётные записи — `account`

| Команда | Что делает | Ключи |
| --- | --- | --- |
| `account create <вход>` | новая учётная запись в принятом домене; пароль для почты — отдельно, `app-password create` | `--name <имя>` |
| `account list` | список по имени входа, страницы проходит сам; столбец «СОСТОЯНИЕ»: ● норма, ▲ квота, × заблокирована | `--login`, `--prefix`, `--after <вход>`, `--limit N` |
| `account get <учётка>` | карточка: псевдонимы, домен, занято, квота, скрытие из книги «Организация» | — |
| `account block <учётка>` | запрет входа; сеансы IMAP, POP3 и push-соединения JMAP закрываются сразу | — |
| `account unblock <учётка>` | снятие блокировки входа | — |
| `account rename <учётка> <имя>` | новое отображаемое имя | — |
| `account set <учётка>` | псевдонимы и скрытие из книги | `--alias <адрес>` (повторяется, заменяет список), `--no-aliases`, `--hidden-from-gal true\|false` |

У записей из каталога (LDAP) `block`, `rename` и `set` отвечают `409`: правьте их в каталоге.

### Пароли приложений — `app-password`

| Команда | Что делает | Ключи |
| --- | --- | --- |
| `app-password create <учётка>` | пароль для IMAP, SMTP, JMAP; значение показывается один раз | `--label <подпись>` |
| `app-password list <учётка>` | пароли без значений, в том числе отозванные | — |
| `app-password revoke <учётка> <id>` | отзыв одного пароля | — |

### Политики — `policy`

Уровень: без ключей — организация, `--domain <домен>` или `--account <учётка>`. Наследование: организация → домен → ящик.

| Команда | Что делает |
| --- | --- |
| `policy get` | заданное на уровне и действующее с учётом вышестоящих |
| `policy set --file <путь\|->` | замена политики уровня целиком из JSON; поля, которых нет в файле, на уровне не заданы |

Поля JSON: `quota_bytes`, `trash_retention`, `retention`, `send_per_hour`, `rcpts_per_hour`, `max_recipients`, `dkim_selector`, `milter_profile`, `trash_purge`, `archive_after`, `archive_quota_bytes`. Без политики: 1000 писем и 2000 адресатов в час, 100 получателей в письме.

```sh
echo '{"send_per_hour": 500, "quota_bytes": 10737418240}' | thepost admin policy set --file - --domain example.ru
```

### Журналы — `audit`, `delivery`

| Команда | Что делает | Ключи |
| --- | --- | --- |

Время — RFC 3339, например `2026-12-01T00:00:00Z`.

### Транспорт — `transport`

Запись идёт по версии снимка: если кто-то изменил настройки раньше, придёт `409` — повторите команду.

| Команда | Что делает | Ключи |
| --- | --- | --- |
| `transport domain list` / `create <имя>` / `delete <домен>` | принятые домены | `--relay host[:port]` — пересылка на внутренний узел |
| `transport source list` / `set <имя>` / `delete <имя>` | доверенные источники (шлюзы и приложения без входа) | `--network <CIDR>` или `--client-cert <dNSName>`; `--xclient`, `--authserv-id`; или `--application`, `--sender`, `--external` |
| `transport route list` / `set <шаблон>` / `delete <шаблон>` | политики доменов назначения (`example.org`, `*.example.org`, `*`) | `--tls opportunistic\|required`, `--pin <SHA256>`, `--smart-host`, `--egress-ip` |

### Чего нет в CLI

В CLI нет команд для: почтовых контактов, подразделений, ресурсов и правил бронирования, отключённых ящиков, очереди исходящей почты, очереди модерации; у групп — «кто может писать», модераторов, скрытия из книги и динамического состава; у учётных записей — представителей, общего доступа к календарям и адресным книгам, списков отправителей, политики аудита; аудита ящиков; общих шлюзов установки; списка организаций. Всё это есть в веб-консоли и в текстовой консоли (F9 — все операции Admin API).

Нет ни в одном интерфейсе, потому что таких операций нет в Admin API: снятия блокировки по перебору паролей, удаления учётной записи, списка сессий и их отзыва. Команды `logout` в CLI нет: сессия истекает сама.

## Веб-консоль администратора

Консоль открывается по адресу `https://<узел>:8443/console/` — её раздаёт сам узел с ролью `admin` на слушателе Admin API (`http.admin.listen`; в поставляемом `deploy/config/all.yaml` — `127.0.0.1:8443`, умолчания у параметра нет: без `http.admin` Admin API и консоль соединений не принимают). Этот адрес бывает только внутренним (loopback или частная сеть): снаружи консоль открывают через VPN или обратный прокси, на публичном 443 её нет.

### Вход

1. Откройте `https://<узел>:8443/console/`. Сертификат должен подходить к имени в адресе; на стенде импортируйте CA стенда.
2. Выберите способ входа — консоль показывает только включённые:
   - **имя входа и пароль** (пароль каталога, пароль приложения или выданный `admin init`); включён, если не настроен `admin.oidc`, иначе — по `admin.password_login`;
   - **«Войти через OIDC»** — если настроены `auth.oidc` и `admin.oidc`;
   - **токен администратора** `tpa_…` — только при выключенном входе по паролю.
3. Сессия живёт 8 ч в этой вкладке браузера (при входе через OIDC — срок токена поставщика). После истечения или перезапуска узла консоль вернёт на экран входа. Выход — пункт «Выход» в меню.

Вход по паролю защищён от перебора: после серии ошибок даже верный пароль отвергается до конца `auth.abuse.block_for` (по умолчанию 15 мин).

### Роли

Роли назначаются в `config.yaml` (`admin.roles`: роль, имена входа, группы каталога). Без записи в `config.yaml` роль есть только у первого администратора: `thepost admin init` делает его администратором установки. Без роли войти нельзя (`403`).

| Роль | Что видит | Что может |
| --- | --- | --- |
| `installation_admin` | все разделы, выбор организации в шапке, вкладка «Транспорт → Инсталляция» | всё |
| `organization_admin` | все разделы своей организации | менять свою организацию |
| `operator` | всё, кроме журнала аудита и аудита ящиков | только читать |
| `auditor` | «Журнал аудита» и «Аудит ящиков» | только читать |

Раздел, недоступный роли, по прямому адресу показывает «Нет доступа».

### Разделы меню

| Раздел | Что там | Действия |
| --- | --- | --- |
| Организация | политика организации (квоты, сроки, лимиты отправки, DKIM, Milter) с действующим значением у каждого поля; политика общего доступа к календарям и адресным книгам | изменить обе политики; подтвердить массовое отключение из каталога |

| Очередь | исходящая почта: получатели, попытки, последняя ошибка, состояние | фильтр по состоянию и адресу; «Повторить» |

### Общее поведение

- В шапке — текущая организация (у администратора инсталляции — список для смены) и имя входа.
- Результат действия — всплывающее сообщение: «Создано», «Сохранено», «Ошибка (код N)».
- Листание: в «Учётных записях» и «Очереди» — «Показать ещё», в журналах и корзине — «Назад» / «Дальше».
- Если настройки транспорта успел изменить другой администратор, узел отвечает `409`, и списки перечитываются.
- Оператор и аудитор видят разделы без кнопок изменения.
- Язык — только русский, тема — светлая; фирменный стиль (UI-19) ещё не подключён.
- Консоль выключается в `config.yaml`: `admin.console.enabled: false`. Консоль на отдельном веб-сервере — архив `console/dist`, рядом `config.json` с `apiBase`, на узле — `admin.console.cors_origins`.

## Текстовая консоль `thepost admin tui`

Текстовая консоль — двухпанельный интерфейс в стиле Midnight Commander для терминала по SSH. Экраны строятся по схеме Admin API, поэтому через F9 доступна любая операция API, даже если для неё нет отдельного раздела.

### Запуск и вход

```sh
thepost admin tui --url https://127.0.0.1:8443 --ca-file /etc/thepost/pki/ca.pem
```

- Ключи: `--url`, `--token`, `--ca-file`, `--insecure`, `--timeout`, `--theme`, `-c, --config`. Адрес — `--url` или `THEPOST_ADMIN_URL`; из `config.yaml` подкоманда его не берёт, иначе впишите в форму входа. `--config` нужен только разделу «Конфигурация узла».
- Есть `THEPOST_ADMIN_TOKEN` или `--token` — вход сразу. Нет — форма: адрес, способ (‹ пароль / токен ›, переключается ←→), имя входа, пароль. Поля — ↑↓ или Tab, вход — Enter.
- Входа через OIDC в форме нет. Токен OIDC, полученный `thepost admin login --oidc`, принимается как обычный токен: через `THEPOST_ADMIN_TOKEN` или способ «токен». Токен `tpa_…` не принимается.
- Нужен терминал не меньше 80×24. Тема — `--theme auto|dark|light|256|16|mono` или `THEPOST_TUI_THEME`; ключ сильнее переменной. При `auto` режим выбирается по окружению: `NO_COLOR` — монохромный с выделением инверсией, `COLORTERM=truecolor|24bit` — полноцветный тёмный, `TERM` с `256color` — 256 цветов, `TERM=dumb` — монохромный, иначе 16 цветов.
- Мыши нет: только клавиатура.
- Выход — F10 или Ctrl+C.

### Экран

| Место | Что там |
| --- | --- |
| верхняя строка | подписи «Установка · Организация · Вид · Сервис · Справка», справа — название и версия |
| левая панель «Ресурсы» | разделы организации, другие организации (Enter — перейти), «Конфигурация узла» |
| правая панель | список, карточка или форма; активная панель — с двойной рамкой |
| низ правой панели | подробности выделенной записи и подсказка по клавишам |
| строка состояния | кто вошёл и на какой узел, число записей; сообщения со знаками ● норма, ▲ внимание, × ошибка |
| строка команды | та же операция командой `thepost admin …` или «нет в CLI: МЕТОД путь» |
| нижняя строка | подписи F-клавиш |

Строка команды помогает перенести ручное действие в скрипт.

### Конфигурация узла

Раздел умеет показывать секции `config.yaml` с описаниями и умолчаниями, править значения (Enter или F4), проверять их `thepost config check` до записи и сохранять копию `config.yaml.bak`. Файл с меткой `# thepost: managed-by=ansible|helm` и файл, на запись в который нет прав, открываются только для чтения.

Раздел работает, когда консоль запущена на самом узле и видит его файл конфигурации: `--config`, `THEPOST_CONFIG` или `/etc/thepost/config.yaml`. Если файла нет (консоль запущена с другой машины), раздел только поясняет, что `config.yaml` правят на узле, а проверяют `thepost config check`.

## Кто с кем и что может

Тип абонента вычисляет ядро по контексту сессии; матрица применяется в коде в точках решения узла — приём iTIP,
бронирование, автоответ, DSN, MDN, группы рассылки, автопересылка, занятость, общий доступ — до любого Sieve
(решение 124; исследование практики — `docs/research/2026-11-14-trust-matrix.md`). Письмо извне применяется к
календарю, только если прошло DMARC и отправлено не представителем (`SENT-BY`). Обновление (`REQUEST`) извне
применяется, если событие с тем же UID уже есть в календаре получателя, организатор тот же, `SEQUENCE` строго
больше, а получатель — участник. В таблице ниже отдельной строки для обновления нет. Ответ (`REPLY`) принимается
от участника события его организатору, отмена (`CANCEL`) — от организатора участнику. Кто может писать в группу,
у группы задаётся отдельно («Кто может писать в группу») и сужает действие матрицы: в новой группе чужим —
закрыто, письмо чужого отклоняется в сессии SMTP.

Снаружи узел принимает только почту (решение 123). Всё, что письмо может сделать само — внести встречу, забронировать
переговорную, вызвать автоответ, переслать себя дальше, — решает матрица доверия: кто прислал или кому уходит
(тип абонента) и какая функция. У каждой клетки есть значение по умолчанию и потолок; администратор меняет значения
только в пределах потолка.

### Типы абонентов

| Тип | Кто это | Как узел его определяет |
| --- | --- | --- |
| Свои | пользователи своей организации | вошёл в систему: submission со входом, JMAP, CalDAV, CardDAV |
| Партнёр | домен из списка партнёров организации | письмо через smtp-in с доменом партнёра в `From` и DMARC pass с выравниванием |
| Сосед по установке | другая организация той же установки (MSSP) | домен принадлежит другой организации узла; пока он не заведён партнёром — как интернет |
| Интернет | все остальные | всё прочее, в том числе письмо через smtp-in с адресом своего домена |

Адрес своего домена в `From` и даже DMARC pass своим не делают: DMARC не проверяет имя ящика, а сторонний сервис,
разрешённый в SPF или DKIM домена, его проходит (RFC 9989 §2.2, §4.1). Заголовкам `Authentication-Results` чужих
серверов и `remote-host` узел не доверяет (RFC 8601 §5, RFC 5183). Соседняя организация — такой же внешний абонент,
как в Exchange Online и Google Workspace: общая установка доверия не даёт.

### Матрица по умолчанию

В клетке — значение по умолчанию, в скобках — потолок, выше которого администратор не поднимет. «Закреплено» —
клетку не меняет никто.

| Функция | Свои | Партнёр | Сосед по установке | Интернет |
| --- | --- | --- | --- | --- |
| Почта | доставляется | доставляется, антиспам и фильтры | так же | так же |
| Новое приглашение (`REQUEST`) | вносится в календарь | письмо с кнопкой (до «авто») | письмо с кнопкой, закреплено | письмо с кнопкой, закреплено |
| Ответ и отмена к нашим событиям (`REPLY`, `CANCEL`) | обрабатываются | обрабатываются (выключается) | обрабатываются (выключается) | обрабатываются (выключается) |
| Прочие методы iTIP (`REFRESH`, `COUNTER`, `ADD`, `PUBLISH`) | по RFC 6638 | нет, закреплено | нет, закреплено | нет, закреплено |
| Бронирование ресурсов | по правилам ресурса | нет, закреплено | нет, закреплено | нет, закреплено |
| Занятость (free/busy) | свободен/занят (до «подробности») | нет (до «ограниченные подробности», для группы) | нет, закреплено | нет, закреплено |
| Общий доступ и публикация календарей | по выбору владельца (до «всё») | нет (до «подробности», ссылкой) | нет (до «подробности», ссылкой) | нет (до «подробности», ссылкой) |
| GAL и поиск по адресной книге | своя книга | нет, закреплено | нет, закреплено | нет, закреплено |
| Делегирование, отправка от имени | по правам | нет, закреплено | нет, закреплено | нет, закреплено |
| Письма в группы рассылки | можно (ограничения группы) | закрыто (до «открыто») | закрыто (до «открыто») | закрыто (до «открыто») |
| Автоответ | внутренний текст | внешний текст, если задан (выключается) | так же | так же |
| Уведомление о прочтении (MDN) наружу | уходит | нет (до «уходит») | нет (до «уходит») | нет (до «уходит») |
| Уведомление о доставке (DSN) | с диагностикой | без диагностики, закреплено | без диагностики, закреплено | без диагностики, закреплено |
| Автопересылка | можно | нет (до «можно»; или для доменов) | нет (до «можно») | нет (до «можно»; или для доменов) |

Значения от узкого к широкому:

- новое приглашение: письмо с кнопкой → «авто» (вносится в календарь);
- занятость, общий доступ и публикация: нет → свободен/занят → ограниченные подробности (время, тема, место) →
  подробности → всё (чтение и запись — только своим);
- письма в группы: закрыто → с модерацией → открыто;
- ответ и отмена, автопересылка: нет → да;
- автоответ и MDN наружу: нет → только ответ на наше письмо → да (значение по умолчанию нигде не стоит —
  решение 124 значения по умолчанию не меняет).

Что стоит за клетками:

- **Письмо с кнопкой.** Приглашение доставляется обычным письмом с частью `text/calendar`; почтовая программа
  показывает «Принять» или «Добавить», и встреча попадает в календарь только действием пользователя. Так Google
  Calendar с 2022 года обращается с приглашениями от неизвестных отправителей; это защита от календарного спама
  (RFC 5546 §6.1.5).
- **Ответ и отмена к нашим событиям** применяются, только если в календаре получателя есть событие с тем же UID,
  отправитель — участник события (`REPLY`) или его организатор (`CANCEL`), а получатель — организатор или участник
  (RFC 5546 §6.1.1–6.1.2, RFC 6638 §11.2, RFC 6047 §2.3). `REPLY` меняет только ответ этого участника. Так делают
  Exchange и Google.
- **Бронирование** — только внутри своей организации: сообщение партнёра или внешнего организатора ресурсу —
  только письмо, без брони и без ответа (Exchange `ProcessExternalMeetingMessages=$false`).
- **Группы рассылки.** Закрытая группа отклоняет письмо чужого ещё в сессии SMTP (`550 5.7.1`), без уведомления
  потом (Exchange `RequireSenderAuthenticationEnabled=$true`). Отказ модератора чужому отправителю не
  уведомляется: такие уведомления — источник backscatter.
- **«Только ответ на наше письмо».** Значение клеток автоответа и MDN наружу, между «нет» и «да»: чужому
  автоответ и уведомление о прочтении уходят, только если его письмо — ответ на письмо, отправленное с узла
  (как письмо признаётся ответом — раздел [Ответы на наши письма и беседы](#ответы-на-наши-письма-и-беседы)).
- **Автоответ** (RFC 3834): чужим — только отдельный внешний текст; пока пользователь его не задал, наружу ничего
  не уходит (как `ExternalMessage` в Exchange). Одному отправителю — не чаще раза в 7 дней, только на адрес
  конверта, с `Auto-Submitted: auto-replied`; на автоматические письма, списки рассылки и пустой обратный адрес
  ответа нет; на письмо в группу члены группы не отвечают.
- **MDN** (RFC 8098): сервер сам уведомлений о прочтении не создаёт. Уведомление, отправленное почтовой программой
  пользователя, уходит чужому адресату, только если клетка открыта.
- **DSN** (RFC 3464, RFC 5321 §6.2): недоставку узел отклоняет в сессии SMTP; если письмо уже принято, уведомление
  идёт на адрес конверта, а не на `From`, и не уходит на явно вредное письмо. Чужим — без диагностики, внутренних
  имён узлов и адресов.
- **Автопересылка** — правила `redirect` и пересылка ящика наружу. По умолчанию выключена: это главный путь утечки
  данных (Microsoft Defender, политика исходящего спама). Внешние участники групп, заведённые администратором,
  автопересылкой не считаются.
- **Занятость партнёру** — только для учётных записей группы, выбранной администратором, и не подробнее
  «ограниченных подробностей» (Exchange Organization Relationship, `FreeBusyAccessScope`).

### Что может менять администратор

**Уровни.** Политика задаётся на трёх уровнях: установка → организация → группа. Значение уровня не шире
действующего значения уровня выше — это и есть потолок. Если учётная запись входит в несколько групп с политикой,
в каждой клетке действует самое узкое значение. Если потолок понизили, а ниже уже стоят более широкие значения,
узел применяет потолок, а экран показывает такие клетки как «выше потолка».

| Уровень | Кто меняет | Что задаёт |
| --- | --- | --- |
| Установка | администратор установки | потолки для всех организаций; клетки «закреплено» не меняются и здесь |
| Организация | администратор организации или установки | значения для организации, домены-партнёры, домены автопересылки |
| Группа | администратор организации или установки | значения для учётных записей группы; для «Писем в группы» — для самой группы |

Каждое изменение — в журнал аудита: уровень, клетка, старое и новое значение. Значение выше потолка не сохраняется:
ответ `422` с перечнем клеток, их потолком и уровнем, откуда потолок пришёл.

**Партнёры.** Список доменов-партнёров ведёт организация. Свой принятый домен партнёром быть не может; домен
соседней организации — может, и тогда она для этой организации — партнёр. Партнёр — доверие к письмам, но не к
бронированию, GAL и делегированию: эти клетки закреплены.

**Если политика недоступна**, узел действует по закрытой матрице: для чужих все функции в самом узком значении.
Почта при этом доставляется.

**Админский Sieve.** Скрипт организации (`thepost admin sieve org put`) выполняется до скриптов пользователей (этап
before) и служит для исключений внутри потолка: сузить, пометить, отбросить. Расширить права он не может.

- Тип абонента скрипт получает расширением `vnd.thepost.peer`: тест `peer` со значениями `own`, `partner`,
  `neighbor`, `external`. Стандартного теста «внутренний или внешний» в Sieve нет.
- `processcalendar` (RFC 9671) вносит новое приглашение сам только от тех, у чьего типа действующее значение
  клетки «авто», то есть сейчас только от партнёров: например, «автоматически — только от организаторов из списка».
  Для остальных типов действие ничего не вносит.
- Узел проверяет скрипт при сохранении: `vacation` в скрипте организации запрещён, `redirect` наружу — только на
  домены, куда разрешена автопересылка. Ошибка — `422` со строкой и столбцом.
- Сбой скрипта организации при выполнении — временный отказ `451 4.3.0`: отправитель повторит позже, а письмо мимо
  скрипта не пройдёт. У Stalwart в таком случае письмо проходит; мы выбрали отказ.
- Скрипт пользователя тоже видит `peer` и может вызвать `processcalendar`, но не шире действующей для него политики.

Пример: автоматически вносить приглашения от двух адресов партнёра, остальные приглашения партнёров оставить
письмом с кнопкой.

```sieve
require ["processcalendar", "vnd.thepost.peer"];
if allof (peer "partner", address :is "from" ["ceo@partner.ru", "pm@partner.ru"]) {
    processcalendar;
}
```

### Когда письмо — ответ на наше

Ответ на наше письмо — признак доверия, а не исключение из проверок. Узел ставит его на входящем письме
(smtp-in), только если выполнены все три условия сразу:

| Условие | Как проверяется |
| --- | --- |
| DMARC pass с выравниванием (RFC 9989) | обычные проверки отправителя; DMARC не пройден — признака нет |
| Отправитель (`From`) — один из адресатов исходного письма | по записи об отправленном ([ниже](#запись-об-отправленном)) |
| Исходному письму не больше `smtp.reply.max_age` | по умолчанию 30 суток |

Привязка к нашему письму — по заголовкам `In-Reply-To`, затем `References`. Message-ID исходящего письма узла
несёт зашифрованную метку — она проверяется расшифровкой, без обращений к базе; чужой Message-ID клиента — по
хэшу в записи об отправленном. Ошибка чтения записи — признака нет (письмо доставляется как обычное), а
заголовок признака, пришедший извне, удаляется до проверок: подставить его нельзя.

Что признак даёт:

- **балл Rspamd.** Узел ставит письму заголовок `X-ThePost-Reply: yes` до фильтров, правило multimap роли
  rspamd снижает балл на `rspamd_reply_score` (по умолчанию −4, символ `THEPOST_REPLY`). Модуль `replies`
  Rspamd не включается: свою вторую таблицу Message-ID узел не ведёт;
- **условие матрицы доверия.** Значение «только ответ на наше письмо» клеток автоответа и MDN наружу
  ([Кто с кем и что может](#кто-с-кем-и-что-может)): чужому автоответ и уведомление о прочтении уходят,
  только если его письмо — ответ на наше.

Чего признак не даёт: антивирус, проверка URL, DMARC и остальные проверки выполняются как для всех писем.
Emotet, Qakbot, IcedID, Squirrelwaffle и TA577 доставляли нагрузку именно ответами в настоящие переписки
с взломанных ящиков (MITRE T1534); отказ и карантин фильтра действуют и для ответа.

Метрики: `tp_smtp_reply_flag_total{result}` — `flagged` (признак поставлен) и `checked` (проверялся,
не подтвердился).

**Аномалии, снимающие признак** (решение 126 г): новый для беседы тип вложения; архив с паролем; образ диска
или ярлык (ISO, IMG, VHD, LNK); ссылка на новый для беседы домен; смена `Reply-To`. Память беседы (типы
вложений, домены ссылок, `Reply-To`) узел собирает уже сейчас; сами детекторы, снятие признака и балл
каталога аномалий — с реализацией решения 126 (SMTP-52).

### Метки Message-ID исходящих

Исходящее письмо узла несёт метку в Message-ID: `tp1.<id>.<base32>@<домен>`. Внутри — XChaCha20-Poly1305
от случайного значения и времени постановки; id ключа — открытым префиксом, nonce случайный. Метка
шифруется, а не подписывается, чтобы не раскрывать время и ящик отправителя.

| Где ставится | Как |
| --- | --- |
| письмо submission и отправка вне сессии без Message-ID | метка вместо отсутствующего заголовка |
| письма узла: уведомления о доставке (DSN), автоответы, iTIP | Message-ID сервера заменяется меткой |
| письмо с Message-ID клиента | не заменяется — ломалась бы копия в «Отправленных» и цепочка у пользователя |

Для писем с чужим Message-ID запись об отправленном ведётся по хэшу заголовка — такой ответ тоже
подтверждается ([ниже](#запись-об-отправленном)), как в Rspamd `replies`.

Метка доказывает только «письмо наше и свежее»: расшифровывается ключом узла, время внутри не в будущем
(запас на рассинхронизацию часов — час). Кто отвечал, метка не доказывает — отправитель сверяется с
адресатами записи об отправленном.

### BATV — метка обратного адреса

BATV (draft-levine-smtp-batv-01) подписывает `MAIL FROM` исходящих наружу: `prvs=KDDDSSSSSS=адрес`. K —
номер ключа набора (0–9), DDD — день истечения (срок `smtp.batv.valid_for`, по умолчанию 7 дней), SSSSSS —
первые 3 байта HMAC-SHA1 от ключа, дня и адреса. Метка считается один раз при постановке в очередь и
хранится в записи: повторы доставки и greylisting видят ту же метку (иначе менеджеры рассылок перестают
узнавать изменённый адрес).

Метку не получают: пустой отправитель (уведомления о доставке), адреса SRS-пересылки, уже подписанный
адрес, адреса и домены `smtp.batv.exempt` (рассылки, ezmlm), а также все письма при пустом наборе ключей.

На приёме проверяются адреса получателей у писем с пустым `MAIL FROM` (bounce) на локальные адреса:

| Случай | `smtp.batv.mode: log` (по умолчанию) | `enforce` |
| --- | --- | --- |
| Метка валидна | снимается, доставка | снимается, доставка |
| Метки нет, истёк срок, чужой ключ, не сходится | доставка; журнал узла и метрика | отказ `550 5.7.1 Bad or missing BATV signature` на `RCPT` |
| Адрес из `smtp.batv.exempt` | метка не требуется | метка не требуется |

Обычные письма (не bounce) доставляются с любой меткой: валидная снимается, невалидная остаётся как есть.
Сбой чтения ключа — адрес как есть: почта не теряется.

Переход `log` → `enforce`. Наблюдайте метрику `tp_smtp_batv_bounces_total{result}`: `valid` (метка
валидна), `missing` (метки нет), `invalid` (не сходится). Отказ в `enforce` находится так:

- журнал доставки: `thepost admin delivery search` — событие с решением `reject` и причиной
  `550 5.7.1 Bad or missing BATV signature`; по Message-ID — лента событий письма;
- журнал узла: строки `smtp: BATV-метка адреса не сошлась` с причиной (`expired`, `foreign key`,
  `bad hmac`, `bad expiry day`, `bad key number`) и `smtp: bounce на адрес без BATV-метки`.

Режим `enforce` включайте, когда `missing` и `invalid` упали до фонового уровня: bounce от систем, не
знающих о метках (старые рассылки, чужие шлюзы), к этому моменту видны и, если нужно, добавлены в
`smtp.batv.exempt`.

### Ключи меток

| Что | Где | Умолчание |
| --- | --- | --- |
| Набор ключей | `smtp.reply.keys` в `config.yaml`: `id` (1–16 байт `[a-z0-9.-]`), `secret` — ссылка на секрет, `active: true` — ровно один в наборе | пусто — метки выключены |
| Значение ключа | хранилище секретов, не меньше 32 байт; в эталоне Ansible — секрет `thepost/reply#<id>` | — |
| Срок признака ответа | `smtp.reply.max_age` | 30 суток |
| Срок метки BATV | `smtp.batv.valid_for` (не больше 498 дней) | 7 суток |
| Кэш ключей | `smtp.reply.key_refresh` | 1 час |

Подписывает новые метки активный ключ, проверяют все — метки прежних писем живут до конца срока. Ротация
без перезапуска: секция `smtp.reply` перечитывается узлом на лету. Порядок: добавьте новый id с
`active: true`, прежний оставьте в наборе; когда ответы на письма со старыми метками перестанут приходить
(не раньше `smtp.reply.max_age`), id уберите. В эталоне Ansible то же: новый id — в начало
`thepost_reply_keys`, прогон роли создаст секрет.

Без ключей (`smtp.reply.keys` пусто): метки Message-ID не ставятся и не проверяются, признак «ответ на
наше письмо» — только по хэшу Message-ID клиента, BATV остаётся в режиме журнала, даже если настроен
`enforce` (отказывать bounce без меток — терять почту рассылок). `thepost doctor` предупреждает
(проверка `smtp.reply.keys`): набор пуст — «метки ответа не ставятся и не проверяются», ключ короче
32 байт или не читается из хранилища — предупреждение с причиной.

### Запись об отправленном

Ключ проверки ответов — запись о каждом письме, поставленном в очередь с внешними или партнёрскими
адресатами: адресаты (в канонической форме), случайное значение метки Message-ID, хэш Message-ID, время
отправки. Содержимого писем в записи нет; локальные адресаты и уведомления о доставке (пустой
отправитель) не записываются — на них не отвечают.

Хранение — не меньше `smtp.reply.max_age` (30 суток по умолчанию); старше чистит обслуживание узла
(шаг `purge_sent_log` роли maintenance). Сбой записи — только в журнал узла: письмо уходит, ответ на него
просто не получит признака.

### Беседы

Беседа — объект JMAP Thread с неизменяемым `threadId` (RFC 8621 §3). При приёме письмо привязывается к
беседе по значениям `Message-ID`, `In-Reply-To` и `References` среди писем учётной записи; нет совпадений —
заводится новая. Беседы не пересекают учётные записи (одинаковые ключи в разных ящиках — разные беседы)
и задним числом не сливаются: письмо, ссылающееся на две беседы, попадает в более раннюю. Привязка,
память аномалий и правила беседы выполняются в одной транзакции с записью письма: сбой привязки
откатывает письмо.

**Правила беседы** — для пользователя, через JMAP `ThreadRule/get|set|changes` (в браузерной почте это
«всегда перемещать», «игнорировать» — как Outlook Ignore и EWS `ApplyConversationAction`):

| Действие | Что делает |
| --- | --- |
| `alwaysMove` (с `mailboxId`) | письма беседы — в заданную папку вместо выбранной правилами Sieve |
| `ignore` | будущие письма беседы — в корзину; окончательное удаление — по сроку корзины |
| `alwaysKeyword` (с `keyword`) | ключевое слово (IMAP-флаг) на письма беседы |

Правило одно на беседу, действует на будущие письма (применяется при приёме); аргумент `applyToExisting`
в `ThreadRule/set` применяет правило и к прежним письмам беседы. Удаление правила письма не возвращает
(как EWS). Удержание администратора пользователь не видит и снять им нельзя.

**Удержание беседы** — для администратора, по образцу Google Vault: удерживается вся беседа, включая
письма, пришедшие после установки удержания. Пока удержание стоит, окончательное удаление писем беседы
(очистка корзины) отвечает отказом; после снятия письма снова удаляются по сроку корзины. Удержание
хранит, кто и когда его поставил и основание — дело, требование, регламент (до 1000 символов).

Команды и маршруты:

| Задача | CLI `thepost admin` | Маршрут Admin API |
| --- | --- | --- |
| Найти беседу письма | `thread find <учётка> --message-id <письмо>` | `GET /api/v1/orgs/{org}/accounts/{account}/threads?message_id=…` |
| Удержать беседу | `thread hold <учётка> <беседа> --reason "дело №42"` | `PUT /api/v1/orgs/{org}/accounts/{account}/threads/{thread}/hold` — тело `{"reason": …}` |
| Снять удержание | `thread unhold <учётка> <беседа>` | `DELETE …/threads/{thread}/hold` |
| Удержанные беседы организации | `thread holds` | `GET /api/v1/orgs/{org}/holds` |
| Выгрузить беседу | `thread export <учётка> <беседа> -o беседа.zip` (без `-o` архив идёт в stdout) | `GET …/threads/{thread}/export` |

`<письмо>` — UUID письма учётной записи из `trash list`, очереди модерации консоли или прошлого
`thread find`; `<беседа>` — UUID из `thread find`. Ответ `find` — UUID беседы, удержание (кто, когда,
основание) и письма в порядке привязки. Повторное удержание заменяет основание.

Права: маршруты бесед доступны администраторам организации и установки; чтение (кроме выгрузки) — и
оператору. Выгрузка отдаёт письма целиком — только администраторам (как темы в корзине). Каждое
удержание, снятие и выгрузка — запись журнала аудита (кто, какой маршрут, при выгрузке — число выданных
писем); запись не сохранена — архив не отдаётся. Хранилище бесед не подключено — маршруты отвечают `503`.

Выгрузка — архив ZIP `application/zip` с письмами `.eml` в порядке привязки (не больше
`admin.max_page_size` писем, имя архива — `<беседа>.zip`). В архив попадают и письма в корзине, и скрытые
«очисткой корзины» (`trash.purge: hide` — заголовками, без тела: снимать скрытие выгрузка не должна);
окончательно стёртых писем в архиве нет.

Интерфейсы: CLI — таблица выше; текстовая консоль — F9 (все операции Admin API по схеме); отдельного
раздела бесед в дереве текстовой консоли и в веб-консоли пока нет.

### Как это делают другие и атаки на доверие

Первоисточники — раздел «(г) Источники» исследования `docs/research/2026-11-14-replies-threads.md`. Коротко:

- **Rspamd `replies`** — таблица хэшей Message-ID исходящих в Redis (срок — сутки) и символ `REPLY` (−4)
  для ответа с совпавшим `In-Reply-To`; вариант без базы — «cookie» в Message-ID с ключом и сроком
  (`cookie_valid_time`, две недели). Наша метка — тот же приём, с шифрованием вместо подписи.
- **Списки разрешённых по исходящей почте**: Mimecast Auto Allow, Outlook Safe Senders (`SFV:SFE`),
  mailbox intelligence в Defender, known senders в Google Calendar. Почти у всех ответ всё равно проходит
  антивирус; Mimecast в 2023 вернул спам-проверку в Auto Allow из-за компрометаций (BEC).
- **BATV** — истёкший черновик IETF 2008 года, не RFC: слабая защита от повтора, метка не привязана к
  содержимому письма; ограничений мы придерживаемся (срок, стабильность при повторах, исключения).
- **Атаки на доверие к ответу**: Emotet отвечал в украденные треды настоящими цитатами с макросным
  документом (ответ приходил через 1 ч 51 мин после заражения); Qakbot и Squirrelwaffle — ответы со
  взломанных ящиков Exchange, которые шлюзы не фильтровали как внутренние; IcedID — ZIP с паролем и ISO;
  TA577 — десятки тысяч ответов с ZIP/HTML для кражи NTLM; поддельный `In-Reply-To` без взлома ловится
  только отсутствием письма в ящике получателя (Ironscales); компрометация ящика собеседника
  (MITRE T1534) проходит SPF, DKIM и DMARC — вся переписка у взломщика есть. Отсюда границы признака:
  минус в балле и условие политики, но не отключение проверок; доверие ограничено сроком и адресатами
  исходного письма.
- **Беседа как единица политик**: Google Vault удерживает тред целиком, Exchange EWS
  `ApplyConversationAction` применяет действия ко всем письмам беседы, включая будущие, Purview eDiscovery
  строит цепочки для выгрузки. Транзакционной семантики для беседы нет ни у кого (в JMAP атомарна каждая
  запись `/set`, но не вызов целиком); у нас привязка «письмо + беседа + политики» — одна транзакция БД.

RFC и черновики: RFC 5322 (Message-ID, `In-Reply-To`, `References`), RFC 5256 (THREAD, раздел
безопасности), RFC 8621 (JMAP Thread, §3), draft-levine-smtp-batv-01 (BATV).

### Первый пользователь от начала до конца (CLI)

```sh
sudo thepost admin init --email admin@example.ru
thepost admin login --user admin@example.ru
export THEPOST_ADMIN_TOKEN=tps_…
thepost admin account create ivanov@example.ru --name "Иван Иванов"
thepost admin app-password create ivanov@example.ru --label Thunderbird
```

Пароль из последней команды показывается один раз — передайте его пользователю. В почтовой программе: логин — адрес целиком, IMAP 993 (SSL/TLS), отправка 465 (SSL/TLS) или 587 (STARTTLS).

### Пользователь не может войти

1. `thepost admin account get <адрес>` — если вход запрещён, `account unblock`.
2. `thepost admin app-password list <адрес>` — не отозван ли пароль; при нужде выпустите новый.
3. После серии неверных паролей срабатывает защита от перебора: блокировка снимается сама по истечении `auth.abuse.block_for` (по умолчанию 15 мин). Снять её раньше ни один интерфейс пока не умеет.

### Переменные окружения

| Переменная | Где | Значение |
| --- | --- | --- |
| `THEPOST_CONFIG` | все команды | путь к `config.yaml` |
| `THEPOST_<СЕКЦИЯ>__<ПАРАМЕТР>` | команды, читающие `config.yaml` | переопределяет параметр: `THEPOST_SMTP__LIMITS__MAX_SIZE=10` → `smtp.limits.max_size` |
| `THEPOST_ADMIN_URL` | `thepost admin`, `tui` | адрес Admin API |
| `THEPOST_ADMIN_TOKEN` | `thepost admin`, `tui` | сессия `tps_…` или токен OIDC |
| `THEPOST_ADMIN_ORG` | `thepost admin` | UUID организации |
| `THEPOST_TUI_THEME` | `tui` | тема: `auto`, `dark`, `light`, `256`, `16`, `mono`; ключ `--theme` сильнее |
| `NO_COLOR` | CLI, `tui` | без цвета |
| `CLICOLOR_FORCE` | CLI | цвет и в конвейере; `NO_COLOR` сильнее |
| `COLORTERM`, `TERM` | CLI, `tui` | фирменные цвета при `COLORTERM=truecolor` или `24bit`, иначе в CLI 16 цветов; `TERM=dumb` — без цвета; в `tui` — выбор режима темы при `auto` |

Пустое значение `THEPOST_ADMIN_*`, `THEPOST_TUI_THEME` и `NO_COLOR` считается отсутствующим.

### Коды выхода

| Код | Значение |
| --- | --- |
| 0 | успех |
| 1 | ошибка или отказ Admin API; `config check` — ошибки конфигурации; `doctor` — есть проверка `fail`; `verify` — есть расхождения или ошибки; `serve` — узел не стартовал или роль завершилась с ошибкой |
| 2 | неверные аргументы командной строки (`--help` и `--version` — 0) |

### Сообщения об ошибках

Данные идут в stdout, ошибки и подсказки — в stderr. Отказ Admin API выглядит так:

```
ошибка: POST /api/v1/orgs/{org}/accounts: 409 Conflict: login a@example.ru занят
подсказка: thepost admin account get a@example.ru
```

Первая строка — метод, путь, код HTTP и текст узла; вторая, если есть, — команда, которая поможет. Ошибки в тексте Sieve выводятся строками «строка N, столбец M: …».

| Код | Чаще всего означает |
| --- | --- |
| 401 | сессия истекла — снова `thepost admin login` |
| 403 | нет роли в `admin.roles` или не хватает прав роли |
| 404 | записи нет или вход по паролю выключен |
| 409 | адрес занят, запись из каталога (правится в LDAP) или настройки транспорта уже изменены — повторите |
| 422 | неверные данные: например, ошибка в скрипте Sieve со строкой и столбцом |

### Ограничения версии 0.2.0

- Один сервер: многоузловой режим и шарды — в следующих версиях. Письма по умолчанию хранятся на диске (`blob.url: file:///…`); хранение в S3 включается в `config.yaml` — `blob.url: s3://<бакет>[/<префикс>]` и секция `blob.s3`; на стенде оно не проверялось (`docs/releases/0.2.0.md`).
- Admin API и веб-консоль слушают только внутренний адрес; роли администраторов задаются только в `config.yaml` (кроме первого администратора от `admin init`).
- Удалить учётную запись нельзя ни в одном интерфейсе — только запретить вход. Исключение — ресурсы: их удаляют в разделе «Ресурсы».
- Снять блокировку по перебору паролей раньше срока нельзя ни в одном интерфейсе.
- `account block` сразу закрывает сеансы IMAP, POP3 и push-соединения JMAP; сеансы ManageSieve и отправки живут до разрыва, новый вход отклоняется.
- Списки отправителей и динамические группы хранятся, но при доставке пока не применяются.
- В CLI нет части операций Admin API ([Чего нет в CLI](#чего-нет-в-cli)).
- Веб-консоль: только русский язык и светлая тема, без импорта из CSV.
- Текстовая консоль: нет мыши и входа через OIDC в форме (готовый токен OIDC принимается); фирменный стиль заказчика не подключён; адрес Admin API из `config.yaml` не подставляется.
- Перехода с бет (`beta-*`, `v*-beta.*`) нет: только новая установка.
