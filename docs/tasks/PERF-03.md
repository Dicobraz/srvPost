# PERF-03 — память простаивающего IMAP IDLE: 981 KB на соединение при пороге 64 KB (Д.7 №17)

Место: `crates/tp-mailstore/` (IMAP IDLE), впервые измерено 2026-11-17 на podium (сэмплер починен, FIX-13).
Фактическое место кода — `crates/tp-imap/` (сессия IMAP и `IDLE`), `tp-mailstore` участвует кэшем списков
(PERF-01); правки волны — `crates/tp-imap/`.

## База

Прогон 20261117T202158Z-speed-base (podium-dev): +100 соединений IDLE → RSS узла 562 → 658 MB,
**981.6 KB на соединение**; порог Д.7 №17 — **≤ 64 KB**. Числа — верхняя оценка (разовые выделения и
остальной рост входят), но разрыв ×15 требует разбора: на каждого «висящего» клиента почты — мегабайт.

## Разбор состояния IDLE-соединения (по коду, стенд агенту недоступен)

Сценарий замера (`deploy/stand/roles/stand_generator/files/probes.py`, `probes.py idle`): соединение TLS
993 → `LOGIN` → **`SELECT INBOX`** ящика нагрузки (~1500 писем, `fill.py --messages 1500`) → `IDLE`;
замер — разность RSS узла между половинами соединений. Что остаётся на соединение и что выделяется
при `SELECT`:

1. **Снимок выбранной папки на соединение** (`crates/tp-imap/src/mailbox.rs`, `select` → `Selected::messages`):
   `Vec<(Uid, MessageId)>` — 24 байта на письмо (UUID `MessageId` + выравнивание), ~36 KB на ящик
   нагрузки и ~240 KB на ящике 10k. Это живёт всё соединение.
2. **Полная выгрузка списка папки на каждый `SELECT`** — `MessageStore::list(All, limit+1)` возвращает
   принадлежащий `Vec<Message>` с метаданными (конверт, дерево частей, превью): даже из кэша PERF-01
   (`crates/tp-mailstore/src/list_cache.rs`, `serve` → `e.list[..n].to_vec()`) это **глубокая копия
   ~0.7–1.5 MB на соединение** (1500 строк × сотни байт метаданных). Список после `SELECT` отбрасывается
   (в снимок идут только uid/id), но аллокатор удерживает арены под повторные выделения такого размера —
   это доминанта 373–981 KB на соединение, размах объясняется размером метаданных и поведением
   аллокатора, а не чем-то ещё.
3. **Буферы чтения/записи**: чтение команд — 16 KB на вызов `read_input` (транзитно), буфер ответа
   `Session.out` — отправка при `Limits::write_buffer` (64 KB), но ёмкость растёт удвоением и остаётся
   до конца соединения (до ~128 KB после больших ответов); в `IDLE` своё чтение 4 KB. Разбор команд
   (`imap-codec` `Fragmentizer`) растёт до наибольшего сообщения — для IDLE-клиентов мал.
4. **Подписка на шину** (`IDLE`, `EventBus::subscribe`): буфер подписчика `tp-meta/signals.rs` пуст до
   первых событий, десятки байт — не вклад. Аудит, регистрация сессии, задача tokio — килобайты.
5. Вне полосы: TLS-сессия `rustls` (~30–50 KB на соединение, `tp-platform`) — нижняя граница после
   устранения пунктов 1–2.

## Как делают другие

- Dovecot держит общий mailbox index папки в памяти (uid → флаги/метаданные) и переиспользует его между
  сессиями; клиентские сессии ссылаются на общий индекс, свои — только номера последовательностей и
  смещения. Cyrus — аналогично (mailbox cache + per-session index pointers).
- Приём общий: данные папки — одна копия с инвалидацией по версии папки, сессии — ссылки. Отличие по
  сути: здесь (класс A, без правок контрактов и `tp-meta`) — снимок `(Uid, MessageId, \Seen)` в кэше
  крейта протокола с инвалидацией по журналу изменений папки, как в кэшах PERF-01/02.

## Сделано (mailstore-17, класс A)

Кэш снимков папок — `crates/tp-imap/src/snapshot.rs`, один на слушателя (`Server::new` →
`Session::with_snapshots`), секция конфигурации `imap.snapshot` ([`SnapshotsConfig`], значения по
умолчанию: `max_bytes` 32 МБ, `max_entries` 1024, `ttl` 600 с):

- **Снимок папки — `Arc<Vec<Row>>`** (`Row` = uid, id, `\Seen`): `SELECT` выдаёт сессии общий снимок
  из кэша — копии на соединение нет. `\Seen` хранится в строке: код `UNSEEN` при выборе (позиция
  первого непрочитанного) считается без чтения метаданных.
- **Свежесть — по журналу изменений папки** (`ChangeLog::message_changes` от базового `ModSeq` записи,
  чтение с лимитом 1): изменений нет — тот же `Arc` (база записи двигается вперёд), есть изменения,
  журнал недоступен или старее базы — полная пересборка (`status` до чтения списка, как в PERF-01 —
  изменения между чтением версии и списка не теряются). Без инкрементальных патчей: `SELECT` читает
  папку один раз за соединение, проверка свежести — чтение журнала с лимитом 1. `ttl` — страховка от
  изменений вне журнала.
- **Правки сессии — `Arc::make_mut`** (`sync` в `idle.rs`, `expunged` в `write.rs`): до первого
  изменения папки снимок сессии общий (соединение `IDLE` без событий — ноль собственной памяти снимка),
  после — своя копия, поведение команд (`FETCH`, `SEARCH`, `STORE`, `COPY/MOVE`, QRESYNC) не меняется.
  `SEARCH` и `FETCH` (`selected.clone()`) теперь копируют `Arc`, не список.
- **Бюджеты**: `max_bytes` (оценка 24 байта на строку), `max_entries` — вытеснение по давности
  обращения; `max_bytes = 0` — кэш выключен (снимок строится для сессии, не хранится). Существование
  папки отдельно не проверяется: `SELECT` разрешает папку деревом до снимка, а удаление папки и её
  писем пишется в журнал — снимок пересоберётся и вернёт ошибку хранилища как раньше.
- **Буферы по факту, без удвоения**: буфер ответа `Session.out` после отправки возвращается к ёмкости
  `write_buffer` (порог отправки), а не к удвоенному объёму; чтение команд — частями по 4 KB (как в
  `IDLE` и POP3) вместо 16 KB на вызов.

Оценка эффекта: простаивающее соединение держит `Arc` снимка (8 байт) + TLS + буферы обмена ~ единицы
KB — вклад полосы mailstore/imap на соединение уходит из сотен–тысяч KB в килобайты; выгрузка списка с
метаданными остаётся только на пересборку снимка (первый `SELECT` папки и после изменений), что и есть
путь PERF-01. Замер порога — на стенде (Д.7 №17, +500 соединений), агенту недоступен.

## Что не сделано

- **Замер Д.7 №17** (агенту недоступен): подтверждение ≤ 64 KB на +500 соединений и отсутствие
  регрессии №5 (сигнал IDLE) — следующий прогон podium/Д.2. Ожидаемый остаток на соединение — TLS
  (`tp-platform`, вне полосы) плюс килобайты буферов; если замер покажет больше 64 KB из-за TLS —
  карточка полосы `platform`.
- **Инкрементальные патчи снимка по журналу** (до `patch_max`, как в кэше PERF-01) — пересборка при
  любых изменениях: по памяти эффекта нет (снимок общий и так), по СУБД — пересборка равна прежнему
  `list(All)` кэша PERF-01. Сделать при первых признаках лишней нагрузки от пересборок.
- **Список для `QRESYNC`-параметра `SELECT`** читается с метаданными мимо снимка (редкий путь: нужны
  флаги и `ModSeq` писем) — оставить как есть до замеров.
- `Fragmentizer` (imap-codec) удерживает ёмкость наибольшего сообщения сессии — после `APPEND` больших
  писем буфер разбора остаётся большим; не влияет на чистый IDLE-профиль, крейт внешний.

Приёмка: тесты крейта (`tests/snapshot.rs`: один снимок на папку для разных соединений, видимость
доставки/флагов/уборки после снимка — пересборка по журналу, CoW сессии после `EXPUNGE`, отказ
`NO [LIMIT]`, вытеснение по `max_entries`, выключение по `max_bytes = 0`) + существующие тесты протокола
(SELECT/FETCH/STORE/MOVE/EXPUNGE/QRESYNC/IDLE) + рассуждение выше; нагрузочный стенд агенту недоступен.

Волна: mailstore-17 (класс A). База прогона — `docs/manual-tests/DEP-13.md`, «Прогон 2026-11-17».
