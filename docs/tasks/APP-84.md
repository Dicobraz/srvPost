# APP-84. Включение журнала в узле — wiring JournalStore/JournalRules в thepost

**Класс:** A · **Волна:** `app-81` · **Ждёт:** `smtp-33` (✅ #153), `meta-61` (✅ #115), `blob-11` (✅ #114), `app-79` (✅ #145)

Хвост волны smtp-33: этап журналирования конвейера (`Delivery::with_journal`) и
точка расширения (`Delivery::with_stage`) реализованы в tp-smtp, но НЕ подключены
в собранном узле — без этой волны журнал в продукте не пишется.

## Сделать

1. **`JournalStore` для узла** (crates/thepost): реализация трейта tp-smtp над
   инфраструктурой узла — индекс `PgJournal` (META-88, схема `journal`) + хранилище
   записей BLOB-18 (бакет журнала, дедуп частей, Object Lock). Запись двухфазная —
   как в контракте (сначала бакет, затем строка индекса; обрыв лечится
   `restore_index`). По образцу порта-адаптера doctor (APP-82, `StorageRecords`) —
   но полная проводка put/read/scan/append, не заглушки.
2. **`JournalRules` над `PgJournal::rules`**: чтение правил журналирования
   организации на каждое письмо (порт tp-smtp; адаптер приложения, образец —
   `with_messages` из #155 в crates/thepost/src/services.rs:542).
3. **Подключение в services.rs**: `Delivery` узла собирается с
   `with_journal(Arc<JournalStage>)`; секция конфигурации `journal` (APP-83, #146)
   управляет: выключена — этап не ставится (нулевое поведение прежнее), включена —
   этап JOURNAL перед Sieve. Источник бакета — тот же провайдер object_store, что у
   BLOB ящиков, но отдельный бакет журнала.
4. `Delivery::with_stage` в узле НЕ подключать (задел модулей SRS 4.10) — только
   упомянуть в док-комментарии.

## Приёмка

- Тест (suite/интеграционный уровня thepost): секция journal выключена — доставка
  без изменений (этапа нет); включена с правилом Both на организацию — запись
  появляется (индекс + бакет), Bcc и раскрытые группы в конверте.
- Существующие тесты doctor (APP-82) и SMTP-53/54 не регрессируют.
