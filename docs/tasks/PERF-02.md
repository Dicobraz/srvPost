# PERF-02 — JMAP Email/query p95 311 мс при пороге 200 мс (Д.7 №1)

Место: `crates/tp-jmap/` (Email/query, Email/get), найдено прогоном Д.7 2026-11-17.

## База

| Прогон | Стенд | query p95 | get p95 |
|---|---|---|---|
| 20261117T174936Z-speed-base | school-99 (8 vCPU, sync_commit=off) | **311 мс** | 383 мс |
| 20261117T182831Z-speed-base | school-99, тише | **311 мс** | 416 мс |
| 20261117T202158Z-speed-base | podium-dev (2 vCPU/3.8G, честный конфиг) | 7.25 с | 11.34 с |

Порог Д.7 №1 — **< 200 мс**. Отказов 0, воспроизводимо 311 мс — стабильный путь, не шум.
На 2 vCPU деградирует в разы: на каждый запрос — заметная работа CPU/СУБД (сортировка/подсчёт?).

## Профилирование (по коду пути, стенд агенту недоступен)

Зонд Д.7 (`probe.js`, k6): `Email/query {sort: [receivedAt desc], limit: 20}` **без фильтра, по всему
аккаунту** (ящик `big` — 10 000 писем), затем `Email/get` этих 20 идентификаторов.

Стоимость одного запроса (всё в слое JMAP, `crates/tp-jmap/src/email_query.rs`, `core/mod.rs`):

1. **`messages_in(scope, None)`** — полная загрузка всех писем аккаунта из СУБД
   (`MessageStore::list(All)` для каждой папки): на ящик 10k — строки `messages` + **`message_parts`
   на 10 000 строк** (slow statement из прогона Д.7, ≈ 1.3 с на медленном диске) + разбор JSONB-метаданных
   каждого письма. Это доминирующая часть — тот же путь, что у IMAP SELECT 10k (PERF-01, 944 мс).
2. `ctx.state()` — статус каждой папки: агрегат COUNT/SUM по всем письмам каждой папки (10k в `big`) —
   заметно, но меньше загрузки.
3. Сортировка в памяти 10k писем компаратором `chain` — миллисекунды; окно (`limit: 20`) — пустяк.

Итог: 311 мс ≈ полная загрузка ящика 10k на каждый запрос; сортировка и COUNT не главные,
COUNT (`calculateTotal`) в измеряемом запросе вообще не запрашивается — «позиционная пагинация
вместо COUNT» уже так: `total` — длина готового списка и только по требованию.

Кандидаты из карточки:
- **Индекс под сортировку по умолчанию** — не выполнен: метаданные писем — полоса `meta`/`mailstore`;
  индекс не убирает передачу 10k строк и частей, то есть не устраняет узкое место. Требуется отдельная
  карточка в `tp-meta` (проекция списка идентификаторов на стороне СУБД, `list_ids` — класс B).
- **Кэш списка ID папки** — сделан (см. ниже).
- **Ограничение total** — уже так (см. выше).

## Как делают другие

- Cyrus IMAP/JMAP (Fastmail) держит в памяти индекс папки (mailbox index: uid → метаданные) и переиспользует
  его между запросами, достраивая по журналу изменений; JMAP `/query` по нему не читает сообщения.
- Dovecot: аналогичный индекс папки (`dovecot.index`) с валидацией по `highest_modseq`.
- Общий приём — кэш/проекция списка идентификаторов с инвалидацией по версии папки, а не COUNT или
  сортировка на стороне СУБД для каждой страницы. Отличие: у Cyrus проекция в store-слое, здесь —
  в слое JMAP поверх контракта `MessageStore` (без межкрейтовых правок, класс A).

## Сделано (jmap-32, класс A)

Кэш в `crates/tp-jmap/src/core/query_cache.rs` (вкл/выкл и лимиты — `jmap.query_cache` в конфиге):
- **`Email/query`**: ключ — (аккаунт, фильтр, сортировка); значение — список идентификаторов в порядке
  сортировки. Инвалидация — токен версий папок (`highest_modseq` каждой папки; изменение письма меняет
  его папку — проверено по всем путям `tp-meta`: приём, флаги, перенос, корзина, очистка, удаление папки).
  При изменениях список **обновляется инкрементально по журналу** (`message_changes` от базы записи,
  до `patch_max` изменений): удалённые убрать, созданные/изменённые перечитать по одному запросу на
  папку и вставить по ключу сортировки. Дорогая полная загрузка — только на холодной записи и при
  переполнении журнала.
- Кэшируются запросы без текстовых термов, цепочек и свёртки, сортировка — `receivedAt`/`sentAt`/`size`
  (это и есть `canCalculateChanges: true`). Текстовые (поиск) и цепочечные — без кэша, как раньше.
- **`Email/get`**: кэш ответа (без `state`) на точный набор аргументов с той же инвалидацией; при
  пересборке письма выбираются **одним запросом на папку** из записи кэша `Email/query` (probe-паттерн
  «query → get»), остальное — точные чтения параллельно (`max_parallel_get`).
- Бюджеты памяти: `max_bytes`/`get_max_bytes` (по умолчанию 64/8 МБ), `max_entries`, `ttl` (страховка);
  вытеснение — по давности обращения. `0` — кэш выключен.
- Состояние аккаунта с версиями папок — `state_full()` (те же запросы, что у прежнего `state()` —
  лишних нет).

Оценка эффекта: повтор и после изменений — без загрузки 10k строк (ожидалось ~десятки мс вместо 311);
полная пересборка остаётся только на холодной записи. Подтверждение — прогон Д.7 (порог < 200 мс).

Приёмка: тесты крейта (прозрачность кэша после приёма/флагов/переноса/удаления, равенство порядка
ключ-сортировки и компаратора, get-кэш, эвикция/выключение) + рассуждение выше; нагрузочный стенд
агенту недоступен. Связано: [[PERF-01]] (та же полная загрузка — не тронута, полоса mailstore).

Волна: jmap-32 (класс A). Связано: [[PERF-01]].
