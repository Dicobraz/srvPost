# PERF-09 — сериализация писателей ящика: mailbox_state FOR UPDATE держит приём (класс B)

Место: путь письма в базу (tp-mailstore/tp-meta — транзакции записи письма, событий и состояния ящика).
Найдено прогонами Д.7 19.11 на эталоне Д.2 после снятия 421-экрана (FIX-18): SMTP 250 p95 1.4–3.6 с при
25 параллельных приёмах, записи DEP-13 «Прогон 2026-11-19».

## Наблюдения

- В пике: `SELECT modseq FROM mailbox_state WHERE tenant_id = $1 AND account_id = $2 FOR UPDATE` —
  elapsed 2.16 с (ждёт блокировку строки ящика); COMMIT 1.2–2.5 с; пул СУБД 32/33 занято, 20+ ожидают.
- В простое тот же COMMIT — 0.5–1.5 мс (fsync диска здоров).
- `synchronous_commit=off` **ухудшает** (SMTP 6.46 с, индексация 78 с против 1.4–3.6 с и 10–32 с при on) —
  узкое место не в fsync, а в конкурентной схеме писателей и длине транзакций.
- beta.3 и beta.4 при честной нагрузке совпадают в пределах шума (SMTP 2.50 с против 1.43–3.59 с) — версия
  беты не при чём; «SMTP 697 мс» 18.11 — артефакт 421 (n=41 из 308).

## Разбор (19.11)

- Транзакция письма уже короткая: блобы и части пишутся в `stage()` до транзакции
  (tp-mailstore/src/ingest.rs), внутри только шесть SQL-операторов (bump modseq, alloc UID, строки,
  части, журнал, события). Забирать из-под замка нечего — узкое место сама очередь на строке.
- Замок до конца транзакции — гарантия порядка: номера журнала (modseq) расходуются в порядке
  фиксаций, иначе клиент синхронизируется мимо ещё не зафиксированного изменения. Снять блокировку
  раньше COMMIT в PostgreSQL нельзя — вариант 2 карты неосуществим.
- Двойного захода доставки в строку нет: sieve применяет флаги в памяти до вставки
  (tp-sieve/src/run.rs); `lock_modseq`-стойки в журнале нагрузки — клиентские set_flags (IMAP/JMAP),
  они разделяют ту же строку аккаунта.
- `insert_batch` уже умеет один bump modseq и один alloc UID на пачку писем.

## Решение (владелец, 19.11)

Меньше блокировок: писатели приёма сериализуются в приложении — один писатель на учётную запись,
окно батча ~5 мс: пришедшие письма пишутся одной транзакцией `insert_batch` — один замок строки на
пачку вместо N. Очередь уходит из блокировок PostgreSQL: пул перестаёт насыщаться, клиентские
операции (set_flags, чтения) теряют ожидание за хвостом приёма. Варианты 1–2 отклонены (см. разбор),
вариант 4 отклонён — порог Д.7 сохраняется.

## Приёмка

- Прогон Д.7 (эталон Д.2): SMTP 250 p95 < 500 мс при 25 параллельных приёмах, отказов нет, потерь нет;
  `FOR UPDATE`-стойки на `mailbox_state` в журнале < 100 мс; пул не насыщен (ожидающих ~0).
- Пороги JMAP < 200 мс / SELECT < 100 мс пересчитать после снятия очереди писателей (JMAP 470/SELECT 140
  сейчас включают то же ожидание).
