# PERF-01 — IMAP SELECT папки 10 тыс. писем: p95 944 мс при пороге 100 мс (Д.7 №2)

Место: `crates/tp-mailstore/` (SELECT/статистика папки), найдено прогоном Д.7 2026-11-17.

## База

| Прогон | Стенд | p95 |
|---|---|---|
| 20261117T174936Z-speed-base | school-99 (8 vCPU, sync_commit=off) | **939 мс** |
| 20261117T182831Z-speed-base | school-99, тише | **944 мс** |
| 20261117T202158Z-speed-base | podium-dev (2 vCPU/3.8G, честный конфиг) | **2.68 с** |

Порог Д.7 №2 — **< 100 мс** (SELECT папки 10 тыс. писем). Отказов нет — путь корректный, но медленный.
Стабильность school-99 цифр (939/944) — не шум: воспроизводимый путь (запрос счётчиков/ unseen по 10k
строк на каждый SELECT?). Пул СУБД ждёт (max 25–64 ожидающих, среднее 3–144 мс) — SELECT, вероятно,
держит соединение и загружает строки.

## Разбор пути SELECT (по коду, стенд агенту недоступен)

SELECT (`crates/tp-imap/src/mailbox.rs`, `select`) делает два вызова контракта; реализация — `PgMeta`
(`crates/tp-meta/`):

1. **`MessageStore::list(scope, mailbox, All, limit+1)`** — `crates/tp-meta/src/messages.rs`:
   - `SELECT …, meta FROM messages WHERE tenant_id=$1 AND account_id=$2 AND hidden_at IS NULL
     AND mailbox_id=$3 ORDER BY uid LIMIT $4` — **все 10 000 строк** папки, каждая с JSONB-метаданными
     (`meta`: конверт, дерево частей, превью); разбор JSONB на каждую строку;
   - `assemble()`: `SELECT … FROM message_parts WHERE … AND message_id = ANY($3)` — вторая выгрузка,
     **≈10 000+ строк** частей по массиву из 10 000 идентификаторов (тот же slow statement из прогона
     Д.7, что и у PERF-02, ≈1.3 с на медленном диске).
   Из списка протокол берёт только счётчики: `Exists` (длина), первое непрочитанное (позиция по
   флагам), карта `uid → id` сеанса, проверка лимита. План: индекс `messages_uid (tenant_id,
   account_id, mailbox_id, uid)` — чтение без сортировки, но это все строки папки (heap + TOAST
   JSONB) — доминанта 944 мс; подтверждено профилированием PERF-02 («тот же путь, что у IMAP
   SELECT 10k»).
2. **`MailboxStore::status(scope, mailbox)`** — `crates/tp-meta/src/mailboxes.rs`: `uid_validity`,
   `uid_next`, `highest_modseq` и счётчики **агрегатом** (LATERAL `count(*)`, `count(*) FILTER
   (WHERE NOT '\Seen' = ANY(flags))`, `sum(size)`) по индексу `messages_uid` — без выгрузки строк,
   заметно меньше первой части.

Итого: SELECT держит соединение и выгружает 20 тыс. строк (письма + части) с разбором JSONB —
это и есть 944 мс и ожидание пула СУБД. Счётчики уже агрегатом; узкое место — полная выгрузка.

## Как делают другие

- Cyrus IMAP (Fastmail) и Dovecot держат индекс папки в памяти (mailbox index: uid → метаданные,
  флаги) и переиспользуют между сеансами/запросами, валидируя по `highest_modseq` и достраивая по
  журналу; SELECT по нему отдаёт счётчики и список без чтения сообщений.
- Общий приём — кэш/проекция списка папки с инвалидацией по версии папки. Отличие по сути: у Cyrus
  индекс в store-слое с проекцией на стороне СУБД; здесь (класс A, без правок контракта и `tp-meta`)
  — кэш списков поверх контракта `MessageStore`, проекция на стороне СУБД (`list_ids`) — отдельная
  карточка класса B (см. «Что не сделано»).

## Сделано (mailstore-16, класс A)

Кэш списка писем папки — `crates/tp-mailstore/src/list_cache.rs`, прозрачный декоратор
[`MessageStore`] (`CachedMessages::new(messages, mailboxes, changes, cfg)`); приложение подключает
его к зависимостям протоколов вместо «сырого» `MessageStore` (`mailstore.list_cache` — секция
конфигурации):

- **Кэшируется `list(All)`** (путь SELECT) — список писем папки по возрастанию UID; остальные
  выборки (`Uids`, `Ids`, `ChangedSince`) — во внутреннее хранилище как раньше.
- **Свежесть — по журналу изменений папки** (`ChangeLog::message_changes` от базового `ModSeq`
  записи): приём, флаги, перенос, корзина и окончательное удаление пишутся в журнал в транзакции
  изменения, поэтому отсутствие записей журнала папки после базы записи = версия папки не менялась.
  Без изменений список возвращается из кэша (проверка — чтение журнала папки с лимитом
  `patch_max + 1`, не дороже самой записи).
- **Инкрементальное обновление по журналу** (до `patch_max`, как в PR #50 / jmap-32): «удалённые»
  проверяются по фактическому существованию (журнал сворачивает «изменено, скрыто и восстановлено»
  в один `destroyed`), созданные/изменённые перечитываются одним запросом `Ids`; список
  поддерживается по возрастанию UID. Изменений больше `patch_max`, список усечён окном или журнал
  недоступен (`Conflict` — база старее журнала) — полная пересборка.
- **База пересборки** — `highest_modseq` папки, прочитанный **до** чтения списка: список отражает
  всё зафиксированное до базы, изменения после базы переигрываются журналом; обратный порядок мог
  бы пропустить изменение между чтением списка и версии.
- Прозрачность: папка исчезла — запись сбрасывается, ответ (в том числе `NotFound`) — из
  внутреннего хранилища; записи согласованы со своей базой (конкуренция — «последний записавший»,
  проверка следующего чтения от базы сохранённой записи); `ttl` — страховка от изменений вне
  журнала.
- Бюджеты: `max_bytes` (по умолчанию 64 МБ; оценка содержимого — строки метаданных, флаги, части),
  `max_entries` (256), `ttl` (600 с), `patch_max` (200); вытеснение — по давности обращения;
  `max_bytes = 0` — кэш выключен. Показатели (`hits`, `patches`, `rebuilds`, `evictions`) —
  `CachedMessages::stats()`.

Оценка эффекта: повторный SELECT ящика 10k — без выгрузки 20 тыс. строк: чтение журнала папки
(малый индексный запрос) + копирование готового списка в памяти — ожидаются десятки мс вместо 944;
первый SELECT и пересборка после больших изменений — без изменений. Также снимает повторную
выгрузку при STATUS и для `Email/get`/`Email/query` tp-jmap (PERF-02) — их вызовы `list(All)`
проходят через тот же кэш при подключении к зависимостям JMAP.

## Что не сделано

- **Подключение в приложении** — полоса `app` (`crates/thepost/src/services.rs`, `Services::imap`/
  `jmap`: обернуть `PgMeta` в `CachedMessages`); без него на стенде эффекта нет. Отдельно — полоса
  `imap` может брать список сеанса `Arc`-ом из кэша для PERF-03 (список папки — один на соединения
  IDLE).
- **Проекция списка идентификаторов на стороне СУБД** (`list_ids`: `SELECT uid, message_id, flags
  FROM messages …` без JSONB и частей — или покрывающий индекс под счётчики `status`) — класс B,
  полоса `meta`/`contracts`: устраняет стоимость первого (холодного) SELECT, кэш её не убирает.
- Замер на стенде Д.7 (агенту недоступен): подтверждение порога №2 (< 100 мс) и отсутствие регрессии
  №5 — следующий прогон после подключения.

Приёмка: тесты крейта (прозрачность кэша после приёма/флагов/переноса/корзины/окончательного
удаления, окна `limit`, вытеснение и выключение, порядок UID после патчей) + рассуждение по плану
запроса выше; нагрузочный стенд агенту недоступен.

Волна: mailstore-16 (класс A). Связано: [[PERF-02]] (тот же профиль нагрузки), база прогона —
`docs/manual-tests/DEP-13.md`, «Прогон 2026-11-17».
