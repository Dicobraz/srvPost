# JMAP-50. Принятие встречи из письма — API веб-почты (решение #134, вариант 3)

**Класс:** A · **Волна:** `jmap-35` · **Ждёт:** `contracts-68` (✅ #125), `smtp-35` (✅ #135)

Решение владельца по issue #134 — **вариант 3**: каноническая точка отказа ручного
iTIP-принятия из спам-письма — отдельное API веб-почты, вызываемое кнопкой
«Принять/Отклонить» в письме. Сервер сам читает письмо, проверяет папку/спам-вердикт
и отвечает — надёжнее сверки ссылки ответа. Защита submission-пути из SMTP-55
(вариант 1, PR #135) остаётся: внешние клиенты (Thunderbird/iOS через IMAP/CalDAV,
REPLY по почте) продолжают получать отказ `550 5.7.1` в tp-smtp; варианты совместимы
(то же хранилище писем, тот же смысл отказа).

## Что делает сервер

1. **Метод JMAP** (полоса jmap; форму — метод расширения `vnd.thepost` или
   переиспользование существующего паттерна EmailSubmission — выбор агента по
   кодовой базе, при развилке — issue «решение»): вход — identity пользователя и
   `emailId` письма-приглашения; выход — результат применения iTIP
   (`accepted`/`declined`/…) либо **ошибка**, если письмо:
   - лежит в папке «Спам» (или её эквиваленте по конфигурации), или
   - имеет спам-вердикт получателя (тот же источник вердикта, что в SMTP-50/SMTP-55:
     DMARC quarantine/reject, карантин Milter, личные списки).
2. Ошибка — структурированная (код + человекочитаемое сообщение для веб-почты):
   «приглашение в „Спаме“ — сначала перенесите письмо». После переноса письма из
   «Спама» (JMAP Email/set или перетаскивание) метод успешно применяется.
3. Применение iTIP — через существующий приём (`ItipDelivery`/ItipInbox,
   `ItipMessage::calendar` из contracts-68 передаётся приёму).
4. **Аудит**: попытка принятия из «Спама» пишется в журнал аудита (отказ — как
   событие), успешное принятие — штатно.
5. **Узел**: точке нужен доступ к `MessageStore` и вердиктам — подключение в
   `thepost/services.rs` (прецедент wiring: ветка `x/smtp-35-node` от SMTP-55;
   при конфликте полосы — отдельная ветка `x/<суть>`, PR только своей полосы).

## Приёмка

- Тест: приглашение в «Спаме» → метод отвечает ошибкой, календарь не меняется,
  в аудите отказ.
- Тест: то же письмо после переноса из «Спама» → метод применяет REPLY, календарь
  обновляется.
- Тест: письмо без спам-вердикта во «Входящих» → метод работает напрямую.
- Существующие тесты SMTP-55 (submission-отказ) не регрессируют.
