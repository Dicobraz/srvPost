## Сделать
- `journal_store.rs` — хранилище записей журнала поверх инфраструктуры tp-blob, отдельное от BLOB ящиков (отдельный бакет/каталог и префикс): запись целиком (письмо + конверт как метаданные) объектом `journal/<YYMMDD>/<JournalId>`; удаление письма пользователем журнал не затрагивает, блокировка журнала не затрагивает хранилище ящиков.
- S3 с Object Lock (SeaweedFS): режим задаёт заказчик — `compliance` (объект не удаляет никто до окончания срока) или `governance` (удаление только ролью с правом обхода, с записью в журнал аудита); срок хранения при записи, продлевать можно только увеличивать. Конфигурация — секция рядом с `blob` (профиль Enterprise).
- Дедупликация внутри журнала: части письма (тело, вложения) — объекты по хешу содержимого, запись ссылается на части; новая ссылка продлевает срок блокировки объекта до наибольшего из ссылающихся записей; части не разделяются с BLOB ящиков.
- Профиль SMB (локальный диск): записи только добавляются сервером, защиты от администратора ОС нет — warning doctor (APP-82); для требований неизменяемости — S3 с Object Lock (SRS 4.9).
- Тесты: запись и чтение обратно (export выдает .eml с конвертом); дедуп — два письма с одним вложением, один объект частей; продление срока при второй ссылке; локальный бэкенд append-only; изоляция — GC BLOB ящиков не трогает журнал, и наоборот.

## Как делают другие
- S3 Object Lock: compliance/governance, retention только продлевается (AWS; SeaweedFS поддерживает governance, compliance, legal hold — https://docs.seaweedfs.com/).
- Отличие: дедуп внутри журнала с продлением блокировки по максимуму ссылающихся записей — чтобы дедуп не ослаблял сроки.

## Приёмка
- Интеграционные тесты против локального бэкенда и MinIO/SeaweedFS (как S3-тесты blob): retention метаданные ставятся, срок только растёт; восстановление индекса (META-88) читает это хранилище.
